# ADR-0003: BattleFormation 결정/실행 분리 — 재배치 커밋 게이트

> 작성 원칙 (README_ko·ADR-0001과 동일): 압축해서 적으면 몇 주 뒤에 내가 못 읽는다.
> 결정은 "왜"를 문장으로 풀어쓴다. 기각한 대안과 그 이유까지 남긴다 —
> 이 문서의 목적은 "이미 끝낸 설계를 나중에 다시 엎으려는 착각"을 막는 것이다.

- **상태**: 채택 (Accepted)
- **결정일**: 2026-06
- **관련 코드**: `UFormationBattleComponent`, `USlotGeneratorStrategy_RangedSafe`,
  `FSlotGenContext`, `APartyManager`(`TickModeDecision`/`SetFormationMode`),
  `FCommitSnapshot`(신규)
- **선행 결정**: ADR-0002 (특히 §3.1 "1인 → 1슬롯" 계약 — 이 ADR은 그 계약 위에서
  GenerateSlot을 *언제* 부르냐를 정한다)

---

## 1. 한 줄 요약

> 영향맵 기반 RangedSafe는 매 틱 슬롯을 재계산·재전달하는 **상시 컨트롤러**가 아니라,
> 트리거가 떴을 때만 한 번 결정하는 **주기적 오라클**이어야 한다. 유닛별 커밋
> 스냅샷(`FCommitSnapshot`)을 두고, **첫 배치 / 사거리 이탈(하드) / 위협 회피(소프트)**
> 트리거에만 재배치하며 그 사이엔 슬롯을 **잠근다**. 플레이어 위치는 트리거가 아니라
> 재배치 *순간의 목적지 편향*으로만 들어온다. 근거리(Arc)는 이 게이트를 쓰지 않는다 —
> 타겟에 고정·1회 배정·타겟 추종이 의도이기 때문.

---

## 2. 맥락 (왜 이 결정이 필요했나)

### 2.1. 증상 — 두 개의 버그

RangedSafe(원거리 안전 위치)를 붙이고 나니 원거리 동료가 이상하게 움직였다.

- **Bug A (이동 중 정지):** 슬롯을 향해 가다 *중간에 멈춰* 서고, 가는 도중 슬롯이
  바뀌면 그쪽으로 방향을 틀었다. 끝까지 도달하지 못하고 어정쩡하게 멈췄다.
- **Bug B (프레임 회전 트위치):** 플레이어가 적 주위를 빙 돌면, *멀쩡히 서 있던*
  원거리 유닛이 갑자기 더 낮은 점수의 슬롯으로 튕겨나갔다. 플레이어 움직임이
  동료의 전투 위치를 흔들었다.

### 2.2. 중간 진단 — 영향맵을 매 틱 "컨트롤러"로 썼다

처음 구조는 매 틱 `GenerateSlot`을 돌려 슬롯을 다시 캐릭터에 밀었다. 영향맵은
"지금 어디가 좋은가"를 답하는 **평가기(오라클)**인데, 그걸 매 프레임 돌려 슬롯을
재전달하면 두 가지가 동시에 터진다.

1. RangedSafe의 후보 0번이 "현재 위치 + Stickiness 보너스"라, 이동 중에 매 틱 평가하면
   ≈제자리를 다시 골라 **이동 중 정지**(Bug A).
2. 전선 방향(FrontlineDir)이 플레이어 위치를 기준으로 잡혀서, 플레이어가 돌면 평가
   프레임 전체가 회전 → 정지 유닛의 유효 슬롯이 더 낮은 점수로 밀려 **쫓겨남**(Bug B).

→ 빠진 것은 **결정/실행 분리 레이어**였다. 영향맵은 주기적으로 "어디로 갈지"만 결정하고,
그 사이의 실제 이동은 locomotion에 맡겨야 한다. 매 프레임 재결정이 문제의 뿌리였다.

## 3. 결정

### 3.1. 결정/실행 분리 — 영향맵은 주기적 오라클, 게이트가 결정한다

유닛별 커밋 스냅샷을 둔다.

```cpp
struct FCommitSnapshot
{
    FVector CommittedSlot = FVector::ZeroVector; // 가기로 확정한 슬롯(환경보정까지 끝난 월드 좌표)
    float   CommitTime    = 0.f;                 // 마지막 커밋 시각 — reluctance 산출 기준
    bool    bHasCommitted = false;               // 한 번이라도 커밋했나
};
```

- 트리거가 떴을 때만 `GenerateSlot` → 환경보정 → 커밋(스냅샷 갱신 + locomotion에 전달).
- 그 사이엔 **홀드**: 아무것도 안 한다. locomotion이 커밋 슬롯까지 알아서 간다(커밋 잠금).
- 즉 영향맵은 "지금 어디가 좋은가"만 답하는 오라클로 돌아가고, "매 프레임 거기로 밀기"를
  멈춘다. 이것이 Bug A의 구조적 해소다(이동 중 재평가가 없으니 ≈제자리를 다시 고를 일이 없음).

### 3.2. 트리거 3종 — 검증은 커밋 슬롯 기준

```cpp
const bool bNeedsReposition =
       !Snapshot.bHasCommitted                                       // 첫 커밋
    || IsSlotOutOfRange(Snapshot, Target, AttackRange)               // 사거리 이탈(하드)
    || ShouldFleeThreat(Snapshot, PerceivedEnemies, TimeSinceCommit);// 위협 회피(소프트)
```

- **사거리 이탈(하드):** 커밋 슬롯에서 타겟을 못 때리면 그 자리는 쓸모없음 → reluctance
  무시하고 즉시 재배치.
- **위협 회피(소프트):** 가장 가까운 적이 회피 반경 안 → 재배치. reluctance 게이트 + 비상
  바이패스(3.4).
- **검증 대상은 `CommittedSlot`(목적지)이지 캐릭터의 live 위치가 아니다.** 이동 중에 캐릭터
  현재 좌표로 검증하면 이동 자체가 노이즈가 되어 트위치가 재발한다. 목적지를 검증해야 한다.

### 3.3. 플레이어는 트리거가 아니다 (Bug B의 근본 차단)

게이트 조건 어디에도 "플레이어와의 거리/방향"은 없다 — **의도적**이다. 플레이어 위치/방향은
재배치가 *이미 트리거된* 순간에 Strategy 내부의 **목적지 편향**으로만 반영된다(아군 쪽으로
약하게). 상시 추적도, 리쉬(leash)도 아니다. 동료는 전투 위치를 지키고 플레이어 궤도를 무시한다.

→ 트리거 경로에 플레이어-상대 프레임(전선 방향 등)을 넣지 않는 것이 Bug B의 근본 차단이다.
("멀어지면 끌어당기기" 같은 요구는 거리가 아니라 **타겟 선정**의 문제다 — ADR-0004 및
타겟 선정 레이어로 미룸. 거리는 "보스와 교전 중이라 멀다"와 "잡몹 쫓아 멀다"를 구분 못 한다.)

### 3.4. reluctance는 이산 타이머가 아니라 연속 가중치

"n초 후 재배치" 같은 이산 타이머가 아니다. **위협 회피 반경을 시간에 따라 0→full로 여는**
연속 가중치다.

```cpp
const float SettleFactor = FMath::Clamp(TimeSinceCommit / FMath::Max(ThreatReluctanceTime, KINDA_SMALL_NUMBER), 0.f, 1.f);
const float EffectiveFleeRadius = ThreatOnTopRadius * SettleFactor;   // 막 배치 직후 0 → 정착하며 full
return Nearest < EffectiveFleeRadius;
```

막 배치한 직후엔 회피를 억제(반경 0)하고, 정착할수록 정상 회피(full)로 연다. 이게
"이동-한대-쫓겨서 또 이동"의 무한 트위치를 "회피 주기당 한 번"으로 줄이는 핵심.
단, **비상(코앞 = `EmergencyFleeRadius`)은 reluctance 무시하고 즉시 회피**(안전 밸브).

### 3.5. 생명주기 — 근본 수정은 호출부 (Activate 방어코드가 아니다)

`SetActive`/`Activate`는 **상태 전환 이벤트**지 매 틱 호출용이 아니다. 따라서 근본 수정은
호출부에서 한다.

```cpp
// PartyManager — 진짜 멱등으로 (주석이 사실이 되게)
void APartyManager::SetFormationMode(EPartyFormationMode NewMode)
{
    if (CurrentFormationMode == NewMode) return;   // 전환될 때만 통과. SetActive를 매 틱 안 때림.
    CurrentFormationMode = NewMode;

    const bool bFollow = (NewMode == EPartyFormationMode::Follow);
    FollowComponent->SetActive(bFollow);
    FollowComponent->SetComponentTickEnabled(bFollow);   // 비활성이면 Tick 자체 정지
    BattleComponent->SetActive(!bFollow);
    BattleComponent->SetComponentTickEnabled(!bFollow);
}
```

추가로:
- `TickComponent` 맨 위에 `if (!IsActive()) return;` — 비활성 포메이션이 다른 모드 동안
  슬롯을 건드려 FollowComponent와 같은 동료를 두고 싸우는 것을 막는 방어.
- **초기화 함정:** 멱등 가드 때문에 시작 모드와 같은 mode로 첫 호출이 들어오면 no-op이라
  컴포넌트 초기 상태가 안 잡힌다. `CurrentFormationMode`를 `None`으로 초기화하고 `BeginPlay`에서
  `SetFormationMode(Follow)`를 한 번 불러 초기 상태를 확정한다. (TickModeDecision은 적이
  없으면 아예 안 불리므로, IsActive 가드를 넣은 뒤엔 시작 시 따라오기가 안 될 수 있다.)
- 호출부가 멱등이 된 순간 `Activate`의 무조건 `Reset()`은 **진입 1회**에만 도니 정확해진다
  (전투 진입 = 새 배치). 그래서 Activate 안의 방어 가드는 **뺐다** — 근본은 호출부이지
  Activate에 방어코드를 쌓는 게 아니라는 판단.

### 3.6. 점유는 "커밋 슬롯"에서 모은다 (Bug 1 수정)

재배치하는 유닛의 점유 입력(`OccupiedSlots`)은, 매 틱 재생성한 임시 슬롯이 아니라 **다른
유닛들의 현재 커밋 슬롯**(남들이 실제로 향하는 확정 위치)을 읽는다. 그래서 같은 그룹 내
동시 생성 충돌(여럿이 한 자리에 몰림)이 구조적으로 사라진다. 커밋 모델이 이 수정을 *가능하게*
했다.

## 4. 결정 과정의 메타 교훈 (미래의 우리에게)

이 버그는 며칠을 끌었고 여러 AI가 증상만 보고 돌았다. 기록할 교훈:

- **교훈 1 — 증상이 아니라 *함수 계약*을 봐라.** 모든 우회의 뿌리는 `Activate`를 "진입
  이벤트"로 오해해 entry-only 로직(`Reset`)을 무가드로 박은 것이었다. 언리얼은 자기 상태를
  멱등 가드로 보호하는데 우리 로직은 안 했다. 표면 증상(매 프레임 재배치)을 백번 봐도
  안 나오고, "이 함수가 뭔가"를 한 번 파니 나왔다.
- **교훈 2 — 성급한 기각.** AI가 한때 "전환 시 뭉텅이로 찍힌다 ≠ 매 프레임"이라는 관찰로
  "Activate/Reset 매 프레임" 가설을 *틀렸다고 단정*했다. 실제론 사용자가 두 코드 상태(가드
  Activate / 무조건 Reset)를 오가며 *두 다른 증상*을 본 것이었다. **격리 테스트가 단일
  진실을 줬다** — 관찰이 엇갈릴 땐 변수를 하나로 줄여라.
- **교훈 3 — "아무것도 안 함"이 정답일 수 있다.** 작동하는 수정(가드 Activate)을 "첫 배치
  이후 동작 안 함 = 고장"으로 오해해 되돌린 적이 있다. 정적 씬에서 커밋 1회 후 홀드는 정상이다.
  트리거가 없으면 안 움직이는 게 맞다. 차이는 *자극을 줘야*(타겟 이동/적 접근/플레이어 궤도)
  드러난다.
- **교훈 4 (ADR-0002의 메타와 같은 결) — 직감을 신뢰하고 끝까지 판 것이 원인을 드러냈다.**
  "AI들이 아무도 못 잡는다"에 굴하지 않고 `Activate`의 정체를 직접 파고든 것, 그리고 막연한
  위화감을 격리 테스트로 언어화한 것이 설계/구현 결함을 드러냈다. 코드 표면도, AI의 확신도
  진실을 보장하지 않는다.

## 5. 기각한 대안

### 대안 A: 호출부는 그대로 두고 `Activate` 안에 방어 가드만 (`if (bReset || !bWasActive)`)

> SetFormationMode는 안 고치고, Activate 오버라이드에서 "이미 active면 Reset 스킵" 가드만 둔다.

**기각(부분 채택 가능).** 증상은 죽지만 **근본(SetActive를 매 틱 때림)이 남는다.** 다른 경로가
SetActive를 또 때리거나, 다른 entry-only 로직이 추가되면 같은 함정이 재발한다. 근본은 "상태
전환 이벤트를 전환 때만 부르기"이고 그건 호출부 멱등이다. (다만 다른 미지의 호출자에 대한
보험으로 한 줄 가드를 *추가로* 남기는 건 무해하다 — 우리는 근본 수정을 택했으니 뺐다.)

### 대안 B: 영향맵을 매 틱 컨트롤러로 유지하고 Stickiness/Hysteresis를 점수로 더 세게

> 결정/실행을 분리하지 말고, 매 틱 평가하되 현재 위치 점수 보너스를 키워 "안 움직이게" 한다.

**기각.** 이동 중 정지(Bug A)와 트위치(Bug B)의 원인이 *점수 안에 박힌 hysteresis*다. 점수를
키울수록 디자이너가 만질 가중치들이 비직교가 되어 튜닝이 불가능해진다("위협이 가까우면
어차피 회피가 이김"). 히스테리시스는 점수가 아니라 **결정 레이어(게이트)**가 소유해야 한다.

### 대안 C: 플레이어 거리/방향을 트리거에 넣기 ("멀어지면 재배치")

> 동료가 플레이어에게서 너무 멀어지면 끌어당기는 트리거를 둔다.

**기각.** Bug B가 그대로 재발하고(플레이어 움직임이 전투 위치를 흔듦), 보스처럼 히트박스가
큰 적에선 넓게 퍼지는 게 정상인데 거리 리쉬가 잘못 끌어당긴다. 거리는 "보스와 교전 중이라
멀다"와 "잡몹 쫓아 멀다"를 구분 못 한다. 이건 **타겟 선정**(후보를 플레이어 교전 구역으로
제약) 문제다 → ADR-0004 + 타겟 선정 레이어로 미룸.

### 대안 D: Arc(근접)도 같은 커밋 게이트로 통일

> 일관성을 위해 근접 슬롯도 트리거 기반 커밋/홀드로 만든다.

**기각.** 근접 슬롯은 타겟에 고정·진입 시 헝가리안 1회·타겟 추종이 **의도된 동작**이다(타겟이
움직이면 따라가는 게 맞고 스래싱이 없다). 게이트는 매 틱 재계산이 *문제가 되는* 개별형
(RangedSafe)에만 적용한다. 근접의 재배치는 타겟 스위칭이 생길 때(타겟 스위치 히스테리시스)
다룬다.

## 6. 결과 (얻는 것 / 치르는 것)

**얻는 것:**

- Bug A(이동 중 정지)·Bug B(프레임 회전 트위치)·Bug 1(동시 생성 충돌)이 동시에 해소.
- 영향맵이 본래 역할인 **오라클**로 정상화. "왜 안 움직이나/움직이나"가 트리거(첫 커밋/사거리/
  회피)로 깔끔히 설명된다.
- **이 유닛별 커밋 모델이 MovementIntent의 씨앗**이다 — [3] 행동 레이어에서 StateTree가
  들어올 때 "커밋된 목적지를 트리거 전까지 잠근다"가 그대로 `HomeSlot`/`RangedRelocation`
  intent로 일반화된다(ADR-0004 §3.9, D8).
- 생명주기 버그를 통해 "Activate는 멱등-ensure-active다"라는 계약을 코드와 문서에 못 박음.

**치르는 것 / 남은 숙제:**

- **RangedSafe 내부의 Stickiness/MoveCost가 vestigial해졌다.** 이제 매 틱이 아니라 *재배치
  순간에만* 도니 거의 무해하지만, 히스테리시스를 게이트가 소유하게 됐으므로 그 둘은 잉여다.
  → **Bug 3(점수축 정규화)** 조각에서 정리·제거. (다음 작업.)
- **튜닝 불변식:** `ShouldFleeThreat`는 타겟을 위협에서 빼지 *않는다*(보스가 돌진해 오면
  물러서야 하므로). 대신 `ThreatOnTopRadius < PreferredRange(= AttackRange × ratio)`를 지켜야
  가만히 선 타겟이 회피 반경 밖이 된다. 안 지키면 자기 타겟에게서 영원히 도망친다.
- T2 드리프트 트리거, staleness 백스톱(연출용 liveness), 타겟 선정(존 앵커링)은 미루어짐.

## 7. ADR-0001 / 0002와의 연결

- **ADR-0002 (1인 → 1슬롯):** 이 ADR은 그 계약 위에서 GenerateSlot을 *트리거 시 1회* 부른다.
  "멤버 순회는 컴포넌트가, Strategy는 1건만"이 그대로 유지되고, 여기에 "그 1건을 *언제* 부르냐"
  (게이트)가 얹힌다. 0002의 §6 "헝가리안과 개별형의 관계" 숙제 중 개별형의 매 틱 재평가 문제가
  이 ADR로 닫힌다.
- **ADR-0001 (A/B = 정책/역학 분리):** 같은 결의 결정이다. 0001은 "점프를 *시도할까*(A)"와
  "점프가 *가능한가*(B)"를 나눴다. 이 ADR은 "*옮길까*(결정 = 게이트)"와 "*어디로/어떻게*
  (생성 = Strategy + 이동 = locomotion)"를 나눈다. 결정과 실행을 섞으면 매 프레임 컨트롤러가
  되어 깨진다는 교훈이 동일하다.
- **ADR-0004 (이동 중재):** 이 ADR의 유닛별 게이트를 여러 레이어에 걸친 **MovementIntent
  중재 모델**로 일반화한다. 커밋 잠금 = HomeSlot/RangedRelocation intent의 우선순위 보존,
  재배치 게이트 = Relocation Gate의 첫 구현. 구체(이 ADR) → 일반(0004) 순서.
