# ADR-0001: Traversal(점프) 결정 권한의 소재

> 작성 원칙 (README_ko와 동일): 압축해서 적으면 몇 주 뒤에 내가 못 읽는다.
> 결정은 "왜"를 문장으로 풀어쓴다. 기각한 대안과 그 이유까지 남긴다 —
> 이 문서의 목적은 "이미 끝낸 설계를 나중에 다시 엎으려는 착각"을 막는 것이다.

- **상태**: 채택 (Accepted)
- **결정일**: 2026-06
- **관련 코드**: `UTacticalTraversalComponent`, `UFormationFollowComponent`,
  `UFormationBattleComponent`, (예정) `CompanionStateTree`
- **선행 결정**: 없음 (첫 ADR)

---

## 1. 한 줄 요약

> 점프를 **시도할지**(정책, A)의 결정권은 "현재 모드의 단일 주체"가 가진다 —
> 평시는 Formation, 전투는 StateTree, 적은 적 AI. 주체는 모드에 따라 **교대하되
> 절대 공유되지 않는다.** 점프가 **물리적으로 가능한지**(역학, B)와 그 실행은
> `TacticalTraversalComponent`가 전담하며, A의 주체가 누구든 무관하게 동작하는
> 공용 도구다.

---

## 2. 맥락 (왜 이 결정이 필요했나)

### 2.1. 두 개의 서로 다른 판단이 하나로 뭉쳐 보였다

점프를 다루다 보면 "점프를 할까?"라는 질문이 하나로 보이지만, 실제로는 성질이
완전히 다른 두 판단이다:

```
판단 A: "지금 이 좌표를 점프로 쫓는 게 맞는가?"   ← 정책 (맥락이 정한다)
판단 B: "그 점프가 물리적으로 가능한가?"           ← 역학 (발밑 지형이 정한다)
```

- **B**는 도약점·착지점·궤적·천장 clearance 같은 순수 역학이다. 누가 점프하든,
  Melee든 Ranged든 적이든, 같은 물리 법칙을 따른다. → **캐릭터에 붙은 공용 도구**가
  맞다. 이미 `TacticalTraversalComponent`가 `ACharacter` + `AAIController`에만
  의존하도록 짜여 있고, `RequestTacticalTraversal(FVector)` 하나가 인터페이스의
  전부다. 이 설계는 옳았다. (단, `AbortTraversal`만 `APartyCharacter`로 캐스트하는
  잔재가 있음 → `ACharacter`로 정정 필요. 아래 9절.)

- **A**는 다르다. "이 슬롯 위치를 점프로 쫓을 가치가 있나"는 **맥락**이 정한다.
  같은 "슬롯이 단차 위에 있음"이라도:
    - 평시 Follow: 리더를 따라 전진하는 단일 의도 → 단차면 넘는 게 자연스럽다.
    - 전투 Battle: 슬롯이 매 틱 적 기준으로 재계산되며 측면·후방으로 흔들린다 →
      "근접 캐릭터가 벽에 몰렸다고 언덕 위로 점프했다가 공격하러 다시 점프로
      복귀"하는 말도 안 되는 현상이 가능하다. 이건 물리적으로는 완벽히 "가능한"
      점프다(B 통과). 말이 안 되는 건 역학이 아니라 **맥락**이다.

즉 A의 답은 **포메이션/상태마다 다르다.** 이것이 처음에 `RequestTacticalTraversal`로
컴포넌트를 분리해 둔 이유였고, 그 직관이 옳았다.

### 2.2. 이 ADR을 쓰게 된 직접 계기 (중요 — 미래의 우리에게)

프로젝트가 커지면서 **위 설계 의도를 잊고 "지금 코드가 비대칭이네 → 합치자"로
직행하는 착각**이 실제로 발생했다. 구체적으로:

> 평가 중 "Battle 컴포넌트엔 점프 판단이 없다 → 책임 위치가 틀렸다 →
> traversal 판단을 캐릭터로 통일해서 내리자"는 결론으로 직행했다.

이것은 **틀린 진단**이었다. 이유:

1. "캐릭터로 내려라"의 근거는 전부 **B**에 대한 것이었다("내 발밑은 나만 안다",
   "Battle도 자동으로 점프 능력을 얻는다"). 이건 B가 이미 캐릭터에 있다는 사실의
   재확인일 뿐, **A를 캐릭터로 내릴 근거가 전혀 아니었다.** 두 판단을 뭉쳐 본 것.

2. "Battle에 A가 없는 것"은 *잘못된 위치*가 아니라 **Battle의 A 정책이 아직
   미구현**인 것이다. 비대칭 ≠ 결함. 의도된 미완성이었다.

3. 내려가는 점프 버그(`ZDiff > +margin`이라 음수 차단)도 "책임 위치" 문제가
   아니라 **Follow의 A 조건이 잘못 작성된 것**이다. 조건을 고치면 되지, 책임을
   옮길 이유가 아니었다.

**교훈: 비대칭을 보면 "왜 원래 분리했는가"를 먼저 물어라. "지금 비대칭이네"만
보고 합치려 들지 마라.** 코드 표면은 설계 의도를 말해주지 않는다. 그래서 이 문서가
있다.

## 3. 결정

### 3.1. A와 B를 분리한다 (이 분단은 *필요한* 분단이다)

```
┌─ 결정 주체 (모드별로 교대, 절대 공유 안 함) ──────────────────┐
│  판단 A: "이 좌표로 점프를 시도할까?"                          │
│                                                              │
│   평시:  FollowFormation        (전진 의도 → 단차면 시도)      │
│   전투:  CompanionStateTree     (state + 역할로 분기, 4절)     │
│   적군:  EnemyStateTree / AI    (자기 맥락대로)                │
│                                                              │
│   → 어느 한 순간, A를 판단하는 주체는 정확히 하나.             │
│     모드 전환 시 결정권이 통째로 넘어간다(이양). 나눠 갖지 않음.│
└──────────────────────────┬───────────────────────────────────┘
                           │ RequestTraversal(좌표)
                           ▼
┌─ 공용 도구 (누가 부르든 불변) ────────────────────────────────┐
│  판단 B + 실행: TacticalTraversalComponent                    │
│   "물리적으로 가능한가?" → 가능하면 실행 (상태머신)            │
│   적·동료·어떤 ACharacter든 동일                              │
└───────────────────────────────────────────────────────────────┘
```

### 3.2. 인터페이스는 좌표 하나 (+ 추후 맥락 힌트)

A의 주체가 B에게 건네는 것은 "이 좌표로 점프 시도해줘"라는 좌표 하나다.
B는 누가 불렀는지(Follow/StateTree/적) 신경 쓰지 않는다. 이 단순함이
"필요한 애가 가져다 쓴다"를 성립시킨다.

### 3.3. "현재 결정 주체가 끝내고 → 캐릭터는 시도 요청 → B가 가능성만 재확인"

캐릭터는 A를 판단하지 않는다("무작정 점프"). 단 이때 "무작정"은 *아무 검증 없이
뛴다*가 아니다 — B(가능한가)는 Traversal이 무조건 본다. 캐릭터/주체가 생략하는
것은 오직 A뿐이다. 물리적으로 불가능한 점프는 B가 알아서 거절한다.

## 4. 전투 내부로 줌인 — 역할(Role) 축의 추가

전투에서 A의 주체가 StateTree로 넘어간다고 할 때, 전투 *내부*를 들여다보면
A의 답이 단일 규칙이 아니라 **2차원 lookup**이 된다:

```
                │ 탐색 중      │ 공격 쿨타임   │ 공격 진입
────────────────┼─────────────┼──────────────┼────────────
Melee           │ 점프 X       │ 점프 X        │ 점프 O (적 치러)
Ranged          │ 점프 O?      │ 점프 O        │ (사거리 기반)
                │ (안전위치)   │ (안전위치)    │
```

- **Melee는 state에 강하게 의존**한다 (탐색/쿨엔 안 뛰고 공격 진입에만).
- **Ranged는 state에 거의 무관**하다 ("안전 위치 확보"라는 특성상, 언제든 뛸
  여지가 있어 점프 우선순위를 낮출 이유가 약하다).

두 축의 소유자가 다르다:

| 축 | 무엇 | 누가 아는가 |
|---|---|---|
| **역할** (Melee/Ranged) | 캐릭터 고정 속성 | BattleComponent (슬롯 전략 고를 때 이미 안다) |
| **전투 state** (탐색/쿨/공격) | 런타임 가변 | StateTree (BattleComponent는 모른다) |

→ 역할은 *어느 정책 테이블*을 쓸지 고르고, state는 *그 테이블의 어느 행*을 읽을지
고른다. 두 축이 만나는 칸이 "점프 O/X"이고, **그 칸을 읽는 주체가 전투 중
결정권자(StateTree)**다.

### 4.1. 따라서 BattleComponent는 A를 완결하지 않는다 (핵심)

직관적으로 "BattleComponent가 역할별 슬롯 전략을 고르니, 점프 정책도 거기에"라고
생각하기 쉽다. **절반만 맞다.**

- 역할 축: 맞다. BattleComponent가 안다.
- state 축: **BattleComponent는 모른다.** "이 캐릭터가 지금 공격 쿨타임인가"를
  알려면 캐릭터 내부 상태를 들여다봐야 하고, 그건 결합이다.

2.1의 패턴이 여기서 재발한다: **BattleComponent가 A를 "완결"하려 들면, 알 수 없는
두 가지(이게 점프해야 닿는 위치인지=B, 지금 뛰어도 되는 state인지=state)를 알아야
하는 모순에 빠진다.** 답: 안 깎는다. BattleComponent는 역할에 맞는 **슬롯 위치만**
반환하고, 점프 여부(A)는 그 좌표를 받은 StateTree가 자기 state를 보고 정한다.

안 2(아래 5절)의 "Formation이 점프까지 고려해 슬롯 반환"을, 전투에서는
"BattleComponent는 위치만 / StateTree가 점프 결정"으로 **분담**하는 것이다.

### 4.2. Ranged의 state-무관성은 이 모델의 검증이다

Ranged의 점프 정책은 거의 모든 state에서 "허용"으로 동일하게 나온다. Melee는
state마다 갈린다. **같은 lookup 구조인데 Ranged는 행마다 답이 같고 Melee는 다를
뿐 — 구조는 하나, 데이터만 다르다.** 이는 "C++는 mechanism, 데이터는 policy"
원칙과 정확히 일치한다: 점프 허용 lookup이라는 *mechanism*은 하나로 두고,
"Melee는 공격 진입만 / Ranged는 항상" 같은 *policy 테이블*은 데이터로 뺀다.
밸런싱 중 "Ranged도 쿨 중엔 안 뛰는 게 낫네" 싶으면 코드가 아니라 테이블만 고친다.

### 4.3. 적군도 같은 구조

몬스터가 특성별로 점프 판단이 다르면, 적은 자기 EnemyStateTree가 결정권자다.
적 나름의 "state + 특성" 테이블을 읽어 A를 정하고, 똑같이 Traversal에 Request한다.
Traversal(B)은 부르는 게 동료든 적이든 구분하지 않는다. 차이는 "누가 어떤
테이블로 A를 결정하느냐"뿐이고, 그건 각자의 StateTree 안에 캡슐화된다.

> ⚠️ **미해결 (이 ADR 범위 밖)**: 역할 구분자가 `ECombatRole` enum인지
> GameplayTag인지 아직 확정 안 됨. 점프 정책 테이블의 **키**가 이 구분자이므로
> 중요하다 — enum이면 컴파일타임 고정 키(닫힌 명확성), GameplayTag면 런타임 계층
> 매칭(열린 유연성). 슬롯 전략엔 태그 유연성이 이득일 수 있어도, 점프 O/X 같은
> 이진 정책엔 enum의 닫힌 명확성이 더 맞을 수 있다. → EQ_2.2 BattleFormation_Range
> 작업에서 결정 후 별도 ADR 또는 본 문서 갱신.

## 5. 기각한 대안

### 대안 1: 이중 판단 (Formation 보정 + Character state 재판단)

> Formation이 슬롯을 보정하며 "점프 필요해 보임" 신호까지 주고, 캐릭터가 그
> 신호를 받아 "내 state상 점프해도 되나?" 한 번 더 거른다.

**기각.** 표면적으론 "두 번 거르니 안전"해 보이지만, 2.1에서 빠져나온 함정의
재발이다.

1. **책임이 두 곳에 쪼개지면 "왜 점프 안 했지?"의 답이 흩어진다.** Formation 보정
   로직과 캐릭터 state 로직 둘 다 봐야 한다. 둘이 서로 "쟤가 막았겠지" 가정하면
   둘 다 안 막거나 둘 다 막는 회색지대가 생긴다. 단일 책임(A)이 두 층에 번지는 것
   = "분리"가 아니라 **누수**.
2. **"Formation이 점프 신호를 준다"는 것 자체가 잘못된 결합이다.** Formation이
   점프 필요를 판단하려면 발밑 역학(B)이나 ZDiff(이미 기각된 신호)를 알아야 한다 →
   Formation이 Traversal의 일을 침범한다. 경계 붕괴.
3. **두 판단이 같은 정보를 보면 중복, 다른 정보를 보면 모순 위험.** 후자라면
   "Formation은 가라는데 state는 서라"는 충돌의 우선순위를 또 third place에서
   정해야 한다. 진실의 출처가 흐려진다.

**다만 미묘한 지점**: 전투 중 "캐릭터가 state로 판단"하는 것 자체는 맞다. 그러나
그것은 Formation 판단에 *덧붙는 두 번째 거름망*(대안 1)이 아니라, Formation을
**대체한 유일한 주체(StateTree)**여야 한다. 거름망 두 개가 아니라, **주체의
교대(이양)**다. 이 구분이 대안 1과 채택안의 핵심 차이.

### 대안 2: BattleComponent가 점프까지 고려해 슬롯을 완성품으로 반환

> 슬롯을 "점프 고려까지 끝낸 완성품"으로 반환하고 캐릭터는 무작정 실행.

**부분 채택 / 부분 기각.** 평시 Follow에서는 이 형태가 그대로 성립한다(결정 주체 =
Formation). 그러나 **전투에서는 기각** — 4.1에서 보았듯 BattleComponent는 state
축을 모르므로 A를 완결할 수 없다. 전투에서는 "BattleComponent는 위치만, StateTree가
결정"으로 분담한다. 즉 "결정 주체가 끝낸다"는 *원리*는 맞되, 그 주체가
BattleComponent가 아니라 StateTree일 뿐이다.

### 대안 3: 판단 A를 캐릭터로 통일해 내린다 (← 우리가 직행했던 착각)

> Battle에 점프 판단이 없으니 책임 위치가 틀렸다. traversal 판단을 캐릭터가
> 일괄로 내리게 하자.

**기각.** 2.2에 상술. A를 캐릭터로 내릴 근거로 든 것이 전부 B에 대한 논거였다.
A는 맥락(포메이션/state)이 정하는 것이지 캐릭터 발밑이 정하는 게 아니다. 비대칭은
미구현이지 오배치가 아니었다.

## 6. 결과 (이 결정으로 얻는 것 / 치르는 것)

**얻는 것:**

- **StateTree 진입이 무료가 된다.** traversal 판단을 Formation 슬롯 보정에 박지
  *않기로* 했으므로, 전투에 StateTree가 들어올 때 "Formation에서 빼서 StateTree로
  옮기는" 작업이 없다. "결정 주체 → Request → Traversal" 경로의 입구에 StateTree를
  끼우기만 하면 된다.
- **적 AI가 공짜로 점프를 얻는다.** Traversal은 부르는 주체를 모르므로 적
  StateTree가 그대로 Request 가능.
- **단일 책임.** 어느 순간이든 A의 주체는 하나 → "왜 점프했나/안 했나"의 답이
  한 곳에 있다.
- **밸런싱이 코드를 안 건드린다** (4.2). 역할×state 정책은 데이터.

**치르는 것 / 남은 숙제:**

- **모드 전환 트리거 문제** (이 ADR 범위 밖): 전투 중 결정 주체가
  Formation→StateTree로 넘어가는 그 전환을 누가/어떻게 트리거하는가. 깔끔하게 안
  풀리면 채택안에도 회색지대가 생긴다. → StateTree 설계 본체에서 다룬다.
- 역할 구분자 enum/tag 결정 (4절 ⚠️).

## 7. 구현 시 작업 순서 (점프 폴리싱 재개 시)

> 현재 로드맵: 전투 포메이션 완료 → (본 점프 작업) → StateTree → Flock.
> 아래는 점프 재개 시점의 순서. 지금 당장 착수 X.

1. **`AbortTraversal`의 `APartyCharacter` → `ACharacter` 캐스트 정정** (독립적,
   5분, B의 재사용성 회복). 9절 참조.
2. **`RequestTacticalTraversal` → `TryBuildPlan` / `StartTraversal` 분리.**
   판정(B)과 실행을 나눠 "B는 됐지만 지금 실행은 보류" 같은 정책 삽입 여지를 연다.
   실행 로직 자체는 안 건드림. (8절)
3. (전투 진입 시) StateTree에서 A를 결정하는 경로 구성. 역할×state 테이블.
4. (추후) 끊긴 구간(평지 갭) 감지 추가. 위/아래 점프와 **실행부는 공유**, 감지
   신호만 이질적(갭은 수직 sweep이 아니라 NavMesh 연속성으로 잡힘 — 8.2).

## 8. 참고: 현재 코드의 분단 상태 (결정과 직접 관련된 부분만)

### 8.1. RequestTacticalTraversal에 판정(B)과 실행이 뭉쳐 있음

`RequestTacticalTraversal`이 ① B 판정(도약점 계산) ② 상태 진입 결정 ③ 명령 발행을
한 함수에서 한다. → "plan은 성공했으나 실행 보류" 정책의 자리가 없고, 호출 측이
점프 여부를 *미리* 알 수 없어 ZDiff 사전 게이트를 호출 측에 따로 둘 수밖에 없었다
(아래 8.3의 원인). `TryBuildPlan`/`StartTraversal` 분리로 해소. **이 분리는 B
내부의 분리이며 A 경계를 건드리지 않는다.**

### 8.2. 위/아래/갭 — 실행은 공유, 감지만 다르다

`TryCalculateTakeoffPoint`가 위/아래를 분기로 욱여넣고 있다.

| 단계 | 위 점프 | 아래 점프 | 끊긴 갭(평지) |
|---|---|---|---|
| 감지 신호 | sweep HIT + 수직 법선 | sweep MISS + ZDiff↓ | sweep MISS + ZDiff≈0 ← **현재 미감지** |
| 도약점 계산 | 벽 앞 후퇴 | ledge 끝 | ledge 끝 |
| 착지 검증 | 공유 | 공유 | 공유 |
| 천장 clearance | 공유 | 공유 | 공유 |
| 포물선 실행 | 공유 | 공유 | 공유 |
| 공중/착지 상태머신 | 공유 | 공유 | 공유 |

→ **다른 것은 감지 신호와 도약점 계산뿐, 실행 파이프라인 전체는 공유.** 갭은
지금 `else → return false`로 떨어져 미감지(ZDiff≈0이라 수직 신호로는 안 잡힘).
나중에 추가할 때 `TryCalculateTakeoffPoint` 안에 if를 또 박지 말고 **감지 함수를
분리**해두면 갭은 한 갈래로 깔끔히 들어온다. (갭의 신호는 "발밑~목표 중간에 바닥이
끊겼나" = NavMesh 연속성 / 중간 ground trace이며, 이는 "ZDiff는 신호가 아니다,
NavMesh 우회량이 신호다"라는 기존 결론과 같은 결.)

### 8.3. Follow의 A 조건이 양수 ZDiff만 통과 → 내려가는 점프 사장

`FormationFollowComponent` Tick의 게이트가 `ZDiff > (MaxStepHeight + margin)`이라
**양수만 통과**한다. 그 결과 `TryCalculateTakeoffPoint` 안의 내려가는 분기
(`ZDiff < -20`)는 일반 루트에서 거의 호출되지 않는다. **이는 책임 위치 문제가
아니라 Follow의 A 정책이 잘못 작성된 것**이다(2.2-3). 조건을 고치면 된다.
