# ADR-0001: ジャンプを「するか」決めるのは誰か — 判断と物理を分ける

> このドキュメントについて：設計上の意思決定を、結論だけでなく「なぜそう決めたか」と
> 「検討して捨てた案」まで残す記録です。コードを読まなくても設計の意図と思考の流れが
> 伝わるように書いています。

- **状態**: 採用
- **決定時期**: 2026-06
- **先行する決定**: なし（最初の記録）

---

## 概要

ジャンプを扱うとき、「ジャンプするべきか」という状況判断と、「そのジャンプが物理的に可能か」
という地形・物理条件の判断が混ざりやすい。このADRでは、その二つを別の責任として分ける。

平時は隊形システム、戦闘中は行動ステートマシン、敵は敵AIが「この場面でジャンプを試みるか」を決める。
一方で、踏み切り地点・着地点・軌道・天井の余裕といった判定と実行は、誰が呼んでも同じように働く
共通の道具が担当する。

重要なのは、ジャンプ処理を単に共通化することではない。  
「するか」を決める主体は場面ごとに交代するが、同時に複数へ分け持たせない。  
「できるか」を調べる物理寄りの処理は共通化する。  
この境界を守ることで、平時・戦闘・敵AIが同じジャンプ道具を使いながら、それぞれ別の状況判断を持てるようにする。

---

## 1. 一言で

> ジャンプを**するべきか**（＝状況判断）を決める権限は「今その瞬間の主体」が一つだけ持つ。
> 平時は隊形システム、戦闘中は行動ステートマシン、敵は敵AI。主体は状況に応じて*交代*するが、
> *共有はされない*。一方、ジャンプが**物理的に可能か**（＝着地点や軌道の計算）とその実行は、
> 誰が呼んでも同じように働く共通の道具が引き受ける。
> 「するか」の判断と「できるか」の物理を、別の担当に分けた。

---

## 2. なぜこの決定が必要だったか

### 2.1. 一つに見えて、実は性質の違う二つの判断だった

ジャンプを扱っていると「ジャンプするか？」は一つの問いに見える。だが実際には、性質が
まったく違う二つの判断が混ざっている。

```text
判断A：「今この場所をジャンプで追うべきか？」   ← 状況が決める
判断B：「そのジャンプは物理的に可能か？」        ← 地形・物理条件が決める
```

- **B**は、踏み切り地点・着地点・軌道・天井の余裕といった、状況判断よりも地形・物理条件に
  寄った判断だ。誰がジャンプしようと ── 近接でも遠距離でも敵でも ── 同じ条件を通る。
  だから**キャラクターに備わった共通の道具**が持つのが自然だ。
- **A**は違う。「この場所をジャンプで追う価値があるか」は**状況**が決める。同じ「目標が
  段差の上にある」でも：
    - 平時（リーダーに追従）：前へ進む一つの意図しかないので、段差は越えるのが自然。
    - 戦闘中：立ち位置が刻々と敵を基準に再計算され、側面や背後へ揺れる。すると「近接キャラが
      壁際に追い詰められたからと丘の上へ跳び、攻撃するためにまた跳んで戻る」という意味不明な
      動きが*物理的には可能*になってしまう。おかしいのは物理ではなく**状況判断**だ。

つまりAの答えは**場面ごとに違う**。これが、最初にジャンプ実行を独立した道具へ分けておいた
理由であり、少なくとも現在の問題に対してはその分割が有効だった。

### 2.2. この記録を書く直接のきっかけ（未来の自分へ）

プロジェクトが育つ中で、**上の設計意図を忘れて「今コードが非対称だ → 統合しよう」へ直行
する誤り**が実際に起きた。具体的には：

> 「戦闘側のシステムにはジャンプ判断がない → 担当の置き場所が間違っている → ジャンプ判断を
> キャラクター側に統一しよう」という結論へ直行した。

これは**誤診**だった。理由：

1. 「キャラクター側へ下ろせ」の根拠が、すべて**B（物理）**の話だった（「自分の足元は自分が
   一番分かる」等）。それはBがすでにキャラクター側にある事実の再確認にすぎず、**A（状況判断）を
   キャラクター側へ下ろす根拠にはまったくなっていなかった**。二つの判断を混ぜて見ていた。
2. 「戦闘側にAがない」のは*置き場所の誤り*ではなく、**戦闘側のA（状況判断のルール）がまだ
   未実装**なだけだ。非対称＝欠陥ではない。意図された未完成だった。

**教訓：非対称を見たら「なぜ元々分けたのか」をまず問え。「今、非対称だ」というだけで統合
しようとするな。** コードの表面は設計意図を語らない。だからこの記録がある。

## 3. 決定

### 3.1. AとBを分ける（これは*必要な*分割だ）

```text
┌─ 判断する主体（場面ごとに交代、決して共有しない） ──────────┐
│  判断A：「この場所へジャンプを試みるか？」                    │
│                                                            │
│   平時：  追従の隊形システム      （前進の意図 → 段差なら試みる）│
│   戦闘：  味方の行動ステートマシン （状態と役割で分岐、4章）    │
│   敵：    敵のAI                  （敵なりの状況で）          │
│                                                            │
│   → 設計上、どの瞬間もAを判断する主体は一つに限定する。       │
│     場面が変わると判断権がまるごと移る（委譲）。分け持たない。 │
└──────────────────────────┬─────────────────────────────────┘
                           │ 「この場所へ」と座標を渡す
                           ▼
┌─ 共通の道具（誰が呼んでも同じ） ──────────────────────────┐
│  判断B＋実行：地形踏破コンポーネント                        │
│   「物理的に可能か？」→ 可能なら実行（状態遷移で）          │
│   敵・味方、どのキャラクターでも同じ                        │
└─────────────────────────────────────────────────────────┘
```

### 3.2. 渡すのは座標一つ

Aの主体がBに渡すのは「この場所へジャンプを試みて」という座標一つだけ。Bは誰が呼んだか
（平時／戦闘／敵）を気にしない。この単純さが「必要な者が持ってきて使う」共通の道具を成立させる。
物理的に不可能なジャンプはBが自分で断るので、Aの主体は「できるか」を直接抱え込まなくていい。

## 4. 戦闘の内側へズームイン — 「役割」という軸が加わる

戦闘でAの主体が行動ステートマシンへ移るとき、戦闘の*内側*を覗くと、Aの答えが単一のルールでは
なく**二次元の表引き**になる。

```text
                │ 探索中   │ 攻撃クールタイム │ 攻撃に入る
────────────────┼─────────┼────────────────┼────────────
近接            │ 跳ばない │ 跳ばない        │ 跳ぶ（敵へ）
遠距離          │ 跳ぶ？   │ 跳ぶ            │ （射程しだい）
                │（安全地）│（安全地）       │
```

- **近接は状態に強く依存**する（探索中やクール中は跳ばず、攻撃に入るときだけ）。
- **遠距離は状態への依存が比較的薄い**（安全な位置を確保する性質上、近接よりも多くの状態で
  ジャンプを許可しうる）。

二つの軸は持ち主が違う：

| 軸 | 何か | 誰が知っているか |
|---|---|---|
| **役割**（近接／遠距離） | キャラクター固定の属性 | 戦闘側システム（立ち位置の戦略を選ぶ時点で既に知っている） |
| **戦闘状態**（探索／クール／攻撃） | 実行中に変わる | 行動ステートマシン（戦闘側システムは知るべきではない） |

→ 役割は*どの表を使うか*を選び、状態は*その表のどの行を読むか*を選ぶ。二つの軸が交わる
マスが「跳ぶ／跳ばない」であり、**そのマスを読む主体が戦闘中の判断権者（ステートマシン）**だ。

### 4.1. ゆえに戦闘側システムはAを完結させない（核心）

直感的には「戦闘側が役割ごとの立ち位置戦略を選ぶのだから、ジャンプの方針もそこで」と
考えがちだ。**半分だけ正しい。**

- 役割の軸：正しい。戦闘側が知っている。
- 状態の軸：**戦闘側は知るべきではない。**「このキャラが今クールタイムか」を知るには
  キャラクター内部の状態を覗く必要があり、それは結合になる。

2.1のパターンがここで再発する：**戦闘側がAを「完結」させようとすると、知り得ない二つのこと
（ジャンプしないと届かない位置か＝B、今跳んでいい状態か＝状態）を知らねばならない矛盾に陥る。**
答え：完結させない。戦闘側は役割に合う**立ち位置だけ**返し、跳ぶか（A）はその座標を受け取った
ステートマシンが自分の状態を見て決める。

### 4.2. 遠距離が状態に依存しにくいことは、このモデルの裏付けになる

遠距離のジャンプ方針は、多くの状態で「許可」に近い答えになる。近接は状態ごとに分かれる。
**同じ表引きの構造なのに、遠距離は行ごとに答えが近く、近接は違うだけ ── 構造は一つ、データが
違うだけ**だ。これは「仕組みはコード、方針はデータ」という方針と一致する。ジャンプ許可の表引き
という*仕組み*は一つに保ち、「近接は攻撃時だけ／遠距離は多くの状態で許可」という*方針の表*は
データへ出す。バランス調整中に「遠距離もクール中は跳ばない方がいい」と思えば、コードではなく
表を直す方向に寄せられる。

### 4.3. 敵も同じ構造

モンスターが特性ごとに違うジャンプ判断を持つなら、敵は自分のステートマシンが判断権者になる。
敵なりの「状態＋特性」の表を読んでAを決め、同じように共通の道具へ座標を渡す。道具（B）は
呼び手が味方か敵かを区別しない。違いは「誰がどの表でAを決めるか」だけで、それは各自の
ステートマシンの中に閉じる。

> ⚠️ **未解決（この記録の範囲外）**: 役割の区別子を固定の列挙にするか、階層的なタグにするかは
> まだ確定していない。ジャンプ方針の表の*キー*がこの区別子なので重要だ ── 列挙ならコンパイル時の
> 固定キー（閉じた明確さ）、タグなら実行時の階層マッチ（開いた柔軟さ）。立ち位置戦略にはタグの
> 柔軟さが利く一方、ジャンプの可否のような二択方針には列挙の明確さが合うかもしれない。後続の
> 作業で決めて、別記録か本文の更新で残す。

## 5. 検討して捨てた案

### 案1：二重判断（隊形が補正し、キャラクターが状態で再判断）

> 隊形システムが立ち位置を補正しつつ「ジャンプが要りそう」というシグナルまで出し、
> キャラクターがそれを受けて「自分の状態的に跳んでいいか」をもう一度こす。

**却下。** 一見「二度こすから安全」に見えるが、2.1で抜け出した罠の再発だ。

1. **担当が二か所に割れると「なぜ跳ばなかった」の答えが散る。** 二つのロジックの両方を見る
   羽目になり、互いに「あっちが止めただろう」と思い込むと、両方が止めない／両方が止める
   グレーゾーンが生まれる。一つの責任（A）が二層へにじむのは「分離」ではなく**漏れ**。
2. **「隊形がジャンプシグナルを出す」こと自体が誤った結合だ。** 隊形がジャンプの要否を判断
   するには足元の物理（B）を知らねばならず、隊形が道具（B）の仕事を侵す。境界の崩壊。

**ただし微妙な点**：戦闘中に「キャラクターが状態で判断する」こと自体は正しい。だがそれは
隊形の判断に*足す二つ目のフィルタ*（案1）ではなく、隊形を*置き換えた唯一の主体*でなければ
ならない。フィルタ二枚ではなく、**主体の交代（委譲）**だ。この区別が案1と採用案の核心の違い。

### 案2：戦闘側システムがジャンプまで考えて立ち位置を「完成品」で返す

> 立ち位置を「ジャンプ考慮まで済ませた完成品」として返し、キャラクターは何も考えず実行する。

**一部採用／一部却下。** 平時の追従ではこの形がそのまま成立する（判断主体＝隊形）。だが
**戦闘では却下** ── 4.1で見たように戦闘側は状態の軸を知るべきではないのでAを完結できない。
戦闘では「戦闘側は立ち位置だけ、ステートマシンが判断」と分担する。つまり「判断主体が完成させる」
という*原理*は正しく、その主体が戦闘側ではなくステートマシンになるだけだ。

### 案3：判断Aをキャラクター側へ統一して下ろす（← 我々が直行した誤り）

> 戦闘側にジャンプ判断がないから置き場所が間違っている。判断をキャラクター側へ一括で下ろそう。

**却下。** 2.2に詳述。Aを下ろす根拠として挙げたものが全部B（物理）の論拠だった。Aは状況
（場面・状態）が決めるもので、キャラクターの足元が決めるものではない。非対称は未実装で
あって、置き場所の誤りではなかった。

## 6. 得たもの／払ったもの

**得たもの：**

- **戦闘へのステートマシン導入がしやすくなる。** ジャンプ判断を隊形の立ち位置補正に
  *埋め込まなかった*ので、戦闘にステートマシンが入るとき「隊形から剥がして移す」作業が少ない。
  「判断主体 → 座標を渡す → 共通の道具」という経路の入口にステートマシンを差し込むだけで済む。
- **敵AIにも同じ道具を再利用しやすい。** 道具は呼び手を区別しないので、敵のステートマシンも
  味方と同じ経路で座標を渡せる。
- **単一責任。** 設計上、どの瞬間もAの主体は一つ → 「なぜ跳んだ／跳ばなかった」の答えを
  一か所に寄せられる。
- **ジャンプ方針の調整をデータ側に寄せやすい。** 役割×状態の方針を表として扱えば、許可条件の
  調整をコード変更から切り離しやすくなる。

**払ったもの／残した宿題：**

- **場面の切り替えを誰がトリガーするか**（この記録の範囲外）：戦闘中に判断主体が隊形→ステート
  マシンへ移る、その切り替えを誰がどう起こすか。きれいに解けないと採用案にもグレーゾーンが
  生じる。→ ステートマシン設計の本体で扱う。
- 役割の区別子（列挙／タグ）の決定（4章 ⚠️）。

## 7. 現在のコード状態についての補足

> 以下は「決定」そのものではなく、決定に関わる現状メモ。実装の細部に踏み込むので、設計の
> 流れだけ追う読者は読み飛ばしてよい。

- ジャンプの「可能か判定」と「実行」が一つの関数に同居しており、「判定は成功したが実行は保留」
  という方針を差し込む余地がない。判定と実行を分ける小さな整理を予定している（この分割はB内部の
  整理で、Aの境界には触れない）。
- 上方向・下方向・平地の切れ目（ギャップ）への対応は、*検知の信号*だけが異なり*実行の流れは
  共通*だ。現在は平地ギャップが未検知（高さ差がほぼ0なので、垂直方向の検知では引っかからない）。
  将来追加するときは、検知の部分を分けておけばギャップも一本の流れに収まりやすい。
- 平時側のジャンプ判断条件が「上方向（高さ差が正）」しか通さないため、下りジャンプが実質的に
  発火しない。これは*置き場所の問題ではなく*、平時側の判断条件の書き方の問題で、条件を直せばよい
  （2.2の3に対応）。

## 8. 他のドキュメントとの関係

これは最初の記録なので先行はない。後続への波及：

- 役割の区別子をどうするか（4章 ⚠️）は、続くADR-0002（立ち位置の抽象化）でその一部に答えが出る。
- ここでの「A（状況判断）とB（物理）を分ける」考え方は、後の決定で繰り返し再現される ──
  「いつ動くか（判断）」と「どこへ／どう動くか（実行）」を分けるADR-0003、立ち位置を決める層と
  移動を実行する層を分けるアーキテクチャ概観など。同じ「判断と実行を混ぜると毎フレームの
  制御役になって壊れる」という教訓の系譜。
