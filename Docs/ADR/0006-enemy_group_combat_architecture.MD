# 0006. 敵グループ戦闘アーキテクチャ — 戦略をモンスターの種別から切り離す

## 概要

敵グループの戦闘AIで最も重要な決定は一つ。**グループとしての戦闘戦略(どの隊形で戦うか)を、
モンスターの種別の中に埋め込まない。**

先に誤解を防いでおく。これは「モンスターが何の行動も持たない」という意味ではない。二つの層を
分けて考える必要がある。

    モンスターの種別が固有に持つもの        グループ/隊形が(配置時に)決めるもの
    ──────────────────────              ──────────────────────
    ・個別の気質                          ・グループの戦闘戦略(隊形)の割り当て
      - 交戦距離(近接/遠隔)                 (包囲 / 遠隔散開 / C隊形 など)
      - 退却の閾値(HPが何%で退くか)        ・スロットの割り当て
      - 攻撃性(クールダウン、交戦間合い)      — 気質をコストとして使い「なるべく
      - 移動速度 など                          似合う形」に並べる(強制ではない)
    ・実際の攻撃方法(コンボ、スキル)       ・ターゲット割り当て / 攻撃トークン配分
      = StateTree / GAS で実行

ここで一つ —「包囲」「C隊形」のようなものは*複数で共に*作る隊形なので、本質的に**グループの
属性**である。一体のモンスターが単独で「包囲」することはできない。逆に「臆病で早く退く」
「射程が長い」といった**個別の気質**はモンスターが固有に持ち、どの隊形に入ってもその中で働く
(後述の決定4「自己都合での離脱」につながる)。

つまりモンスターは「自分はこういう気質で、こう攻撃する」を持つ。**ただし「グループ全体がどの
隊形で戦うか」はモンスターではなくグループ単位で決まる。** 種別に固定しないのはこのグループ
隊形だけであり、個別の気質と攻撃方法はそのまま生きている。

この切り分けが以下をすべて可能にする。(逆に、グループ隊形をモンスターの種別に固定すると、
多様性と戦略性はすぐに衝突する。)

- モンスターのパターンに触れずに、その上へ戦術AIを乗せる
- 異なるモンスターを一つのグループに混ぜる
- 特定の配置でのみ別の戦略を使う
- 特定の地域/遭遇で、種別と無関係な戦略を適用する

> この文書は設計判断の記録である。実装はまだ着手前であり、StateTree/GAS との連携は、現在
> 確定した判断と混ざらないよう「まだ確定していないこと」に分けて置く。

---

## 問題 — 四つの課題

### 課題1. モンスターのパターンを侵さずに戦術AIを組めるか

新しいモンスターが入るたびにグループの戦術コードが*そのモンスターの攻撃パターンまで*知る必要が
あると、追加するほどコードが重くなる。

問題の核心はここだ —グループ戦略が「ゴブリンにコンボ3を出させろ」と*言った瞬間*、グループ
戦略は特定のモンスターのパターンに縛られる。新しいモンスターを入れるには、グループ戦略を
また直さねばならない。

### 課題2. 異なるモンスターを混ぜて配置できるか

逃げるのが上手い敵、攻撃的な敵、遠隔の敵、包囲を好む敵 — これらを同じ場所に配置しつつ、
それぞれの性格を生かしながら一つのグループのように動かしたい。

### 課題3. 多様性と戦略性は両立できるか

モンスターごとに違う個別の気質(臆病、攻撃的、射程が長い)を与えれば多様性は生まれる。これは
モンスターが持つべきものだ。問題は**グループとしての隊形(包囲・散開)までモンスターの種別に
固定したとき**に起こる。「包囲モンスター」というクラスが包囲隊形のロジックそのものを抱えて
いると、そのゴブリンは別の隊形(退却・C隊形)に参加できない — 包囲がクラスに縛られているからだ。

つまり多様性(個別の気質)はモンスターに置き、隊形(グループ戦略)はモンスターの外へ出して
こそ、両者が両立する。

### 課題4. モンスターの種別を越えた戦略が可能か

こういう設計をしたい。

    Aだけのとき    → Aの基本戦略(Aどうしで包囲)
    Bだけのとき    → Bの基本戦略(Bどうしで遠隔)
    A + B が揃うと → C戦略 — AとBを「一つの隊形にまとめて」再編成
                            (Aは前列、Bは後列)
    特定の地域では  → 種別と無関係に D戦略

ここで注目したい点が一つ —**A+BのCは、単に「戦略を変える」だけではない。** Aだけのときは
Aどうしで一つの群れ、BだけのときはBどうしで一つの群れだが、Cは*AとBを一つの隊形*に合わせる
(前列-後列が一つの陣形だから)。つまり**「いくつのグループにまとまるか」自体が戦略によって
変わる。**

    Aだけ / Bだけ:  種別ごとに別々  → 2グループ
    A + B の C:     一つに合わせる  → 1グループ

これが可能になるには、(1)戦略がモンスターの種別に固定されていてはならず、(2)「何を一つの
グループにまとめるか」が固定ではなく配置ごとに変わりうる必要がある。前者は「中核の決定」、
後者は「決定1」で扱う。

**四つの課題に共通する罠:** グループ隊形をモンスターの種別に固定すると、1〜4がすべて塞がる。
だからすべての決定の根は「グループ戦略を種別から切り離す」こと一つだ。

## 中核の決定 — グループ戦略とモンスターの正体を切り離す

### 融合した構造(罠)

グループ戦略をモンスターのクラスの中に入れると、こうなる。

    包囲ゴブリン
      - ゴブリンである
      - 包囲戦略を直接持つ     ← 種別と戦略が一つのクラスに縛られる
      - 包囲スロットを直接作る
      - いつ攻撃するかも直接決める

ここでは「ゴブリン」と「包囲戦略」が一体だ。だから:
- 同じゴブリンを別の戦略(退却)に入れられない — 包囲ロジックがクラスに縛られているから。
- A+B→Cも不可能だ — 連携ロジックがどのクラスにもなく、新クラスを作るか両方に分岐を足す
  しかない。種別が増えるほど組み合わせが爆発する。
- マップD戦略も不可能だ — すべてのモンスタークラスに「マップDなら隊形」のコードを入れねば
  ならない。

**だからグループ戦略を種別に固定すると、多様性と戦略性は本当に両立できない。** これは杞憂
ではなく、実在する設計上の欠陥だ。

### 切り離した構造(採用)

グループ戦略をモンスターの外へ出し、グループに*割り当てられる*別の方針として置く。

    モンスターが持つもの                  グループに割り当てられるもの
      - そのモンスターの個別の気質           - 今このグループが使う戦略(隊形)
      - 交戦距離、退却の閾値、攻撃性          - ターゲット割り当て
      - 実際の攻撃方法(StateTree/GAS)       - スロット生成
                                            - 攻撃トークン配分
                                            - グループの姿勢(posture)

モンスターは「自分はこういう気質で、こう攻撃する」までを知る。実際のグループ戦術の判断は
グループ戦略が行う。(攻撃方法そのものは依然モンスターが持つ — 概要の二層の区分のままだ。)

こう切り離すと**「包囲モンスター」という言葉の意味が変わる。** もはや「包囲ロジックを*持つ*
モンスター」ではなく、*「包囲隊形によく編成されるモンスター」*だ。戦略そのものはモンスターの
外、グループに割り当てられる対象になる。すると A+B→C は「判断層が編成(roster)を見てCを*選ぶ*」
ことであってモンスターのコード分岐ではなく、マップDも単に割り当てを変えることになる。

**多様性(種別ごとの気質)と戦略性(グループ方針、合成・上書き)は、両者を*切り離したからこそ*
共存する。**

ここで一つ先に触れておく — 課題2(混ぜる)と課題4(合成)は難易度が違う。課題2は*共存*だ
(AグループとBグループが同じ空間にいても、互いに独立だから単に共存する)。これは層を分ける
ことで既に解ける。課題4は*合成*だ(複数の要素が合わさって新しい戦略が生まれる)。これが本当に
難しいところで、以下の決定がそれを扱う。

## 決定1 — グループの境界は、モンスターの種別ではなく「配置」が作る

まず決めるべきは「何を一つのグループにまとめるか」だ。そしてここでの核心は —
**グループはあらかじめ存在するのではなく、配置データが生み出す*結果*だ。**

素朴に考えると「実行時に近くにいる敵を自動でまとめる」が浮かぶ。だがそれだと、誰が一つの
グループかを毎回距離で計算せねばならず、設計者が「この二つは一つの陣形」と意図する方法がない。
だから逆にする —**スポーンプール/遭遇のデータが「このメンバーたちは一つのグループ」と決める。**

なぜ重要かは(課題4で触れたとおり)同じA, Bを二か所に配置してみると見えてくる。

    地域 X:                          地域 Y:
      Aグループ ─ 包囲戦略             A + B 統合グループ一つ ─ C戦略
      Bグループ ─ 遠隔戦略               Aは前列、Bは後列へ再編成
      = 種別ごとに分かれた2グループ      = 種別が混ざった1グループ

**同じA, Bなのに、Xでは2グループ、Yでは1グループだ。**「グループ」という境界そのものが、
配置の戦略によって変わる。Xは「種別ごとに分けてそれぞれ行動」、Yは「全部まとめてC戦略」。
だからグループの境界はモンスターの種別だけでは決まらない — 配置が決める。

この方式の大きな利点:**グループの戦略がスポーン時点で決まるので、実行時に「このグループは
何の戦略か」を計算する必要がない。** 配置データが「このメンバーたち = この戦略」をあらかじめ
持っていて、スポーンのときにそのまま展開すればいい。位置を見て判断したり編成を分析したり
する必要がなくなる。

> 具体的なクラス名はまだ確定しない。今確定するのは方向だ —**グループの境界はモンスターの
> クラスではなく、スポーン/遭遇のデータから来る。**

## 決定2 — 合成は全体ルールではなく「配置単位」で点ける

「A+Bが揃うとC」をどう発動させるか。ここでの罠は —**組み合わせそのものを引き金にすること**だ。

    悪い方向(組み合わせが引き金):
      ゲーム全体で A + B の組み合わせなら必ず C

なぜ悪いかは場面で見ると明らかだ。ある場所でAとBを連携させたくてこのルールを点けると —
**ゲーム全体のすべてのA+Bの遭遇が連携になってしまう。** 通常フィールドでたまたまAとBが一緒に
いるだけで、急に連携隊形を組む。設計者が「ここだけ」を表現できない。

だから合成を**配置(スポーンプール)の属性**として置く。

    良い方向(配置が合成を点ける):
      このスポーンプールでは A + B を C にまとめる
      あのスポーンプールでは A と B を別々に置く
      通常フィールドのスポーンプールには合成ルールが無い → A+Bでも各自で行動

核心は**「合成しない」が特別な場合ではなく既定値**だということだ。通常フィールドのプールは
合成ルールが*空なので*合成が起きない。「ここでは合成するな」というコードを別に書く必要が
ない — ルールが無ければしないのが自然な動作だ。設計者は望むプールにだけルールを入れる。

こうして同じモンスターの組み合わせでも、配置の意図によって違う見せ方ができる。A+BがXプール
では各自で戦い、Yプールでは C隊形を組む — 両者の違いは*そのプールが合成ルールを持つか*だけだ。

#### なぜ「マップの地域」ではなく「スポーンプール」か

最初は「特定の地域(マップ上の範囲)に入ったら合成」も候補だった。だがそれは*実行時にグループが
どの地域にいるかを判定し続ける*必要がある — グループが動き回って境界を出入りすれば、その都度
位置の確認が要る。それは結局、空間分割の問題に戻る(ADR-0005でシンプルに行くと決めた、あの
負担だ)。一方スポーンプール依存は*スポーン時点で一度*決まって終わる。だから実行時の位置判定が
不要なスポーンプール依存を選ぶ。

> 具体的な実装(プールの設定 / 遭遇データ / 別のルール対象)はまだ確定しない。

## 決定3 — 役割とモンスターの種別を切り離す

C戦略は「Aは前列、Bは後列」のようにメンバーを*役割ごとに違う形*で配置する。ここで決めるべき
ことがある —**その役割にモンスターの種別を固定するか?**

    悪い構造(役割に種別を固定):
      C戦略 {
        役割1 = Aモンスター専用     ← 種別が役割に固定される
        役割2 = Bモンスター専用
      }

こう固定すると二つが壊れる。**D+Eを入れたら?** CはA, Bしか知らないので動かない。
**A, Bの順番を変えたら?** 変えられない。そしてより根本的に — これは私たちがずっと拒んできた
「戦略=種別の融合」が*一段下で*再発したものだ。種別を戦略の外へ出したのに、役割にまた種別を
固定すれば、元へ戻ってしまう。

だから**C戦略は「役割」だけを知り、「種別」を知らない。**

    採用する構造(役割は種別を知らない):
      C戦略 {
        前列の役割 ×N   ← 誰が埋めるかは尋ねない
        後列の役割 ×M
      }
      + 配置ルール: 各モンスターの気質を見て「前列に似合う/後列に似合う」で並べる

Cは「前列の役割N個、後列の役割M個」という*構造*だけを定義する。誰が前列を埋めるかは、各
モンスターの気質(交戦距離など)を見て並べる。すると:
- **B, Aの順番を変えればBが前列になる** — Cは種別を知らないので、誰が前列に似合うかが変われば
  配置も変わる。望んだ柔軟さが*種別を固定しなかったからこそ*ついてくる。
- **D+EもCに参加できる** — Cは「A+B専用」ではなく「前列に似合うもの + 後列に似合うもの」を
  求めている。D, Eのうち誰が前列に似合い誰が後列に似合うかの問題に置き換わる。

戦略は*役割を求め*、配置は*各モンスターの気質を見てどの役割に合うか並べる*。この切り分けが、
Cを「A+B専用コード」にしないでくれる。

#### 「似合う」は強制ではなく並べ替えだ(決定4とのつながり)

ここではっきりさせておく — 「前列に似合う/後列に似合う」は*禁止ではなく重み*だ。近接は前列の
点が高く遠隔は後列の点が高いが、これは「遠隔は前列*禁止*」ではない。グループに遠隔しかいなければ、
遠隔が前列に配置される(点が低いだけで、入る)。この「似合う」値もモンスターが別に持つ属性では
なく、配置が*気質(交戦距離)から算出する*。つまり配置をより妥当な既定値にするための仕組みで
あって、設計者の配置を強制しない。(なぜ強制しないかは下の決定4で扱う。)

## 決定4 — 「まずい配置」は許し、「動作が破綻する場合」だけ扱う

設計者が非効率な配置をすることはある。遠隔モンスターを前列に入れれば弱いだろう。だが
**これをシステムが強制的に防ぐべきか?** ここで線を引く必要がある — すべての状況を防ぐのは
不可能で、シニアの仕事は*何を扱い、何を設計者に開くか*を意図して引くことだ。

基準は一つ:**「動作が破綻するか」対「選択がまずいか」。**

#### 開いておくもの — まずいが動作する配置

遠隔を前列に置けば非効率だ。だが*動作は正常だ* — 遠隔が前で撃つだけだ。そして「遠隔を前列に
置くのは常に間違い」とシステムが強制すれば、設計者が「この遭遇は遠隔を囮として前に立てる」と
意図する道を閉ざす。それは設計者の領域を侵すことだ。

    遠隔が前列で撃つ = 非効率だが動作する = 設計者の責任。開いておく。

#### 扱うもの — 位置の制御権の衝突

近接モンスターを後列に入れたときは違う。近接は攻撃するには前へ出る必要があるのに、Cは後列に
いろと言う。この二つが毎フレーム互いに位置を上書きすると、こうなる。

    C戦略:「後列へ!」 ┐
    攻撃の欲求:「前へ!」┴→ 後列へ引かれる → 前へ出る → また引かれる → 振動(ガタつき)

これは「非効率」ではなく*位置を制御する主体が二つに分かれて互いに争う*状況だ。制御権が一つに
まとまらず、ガタつく。これは設計が扱うべきだ。

#### 扱う方法 — 一度に一つだけが位置を制御する

ガタつきの原因は「衝突」そのものではなく*二つのシステムが同時に位置を制御する*ことだ。だから
状態で分けて、ある瞬間には一つだけが位置の制御権を持つようにする。

    Hold    : スロットが位置を制御(後列にとどまる)
       ↓ 攻撃のタイミング + トークン
    Commit  : 攻撃が位置を制御(前へ出て斬る)
       ↓ 攻撃が終わる
    Return  : スロットへ復帰 → Hold

Cが後列へ引くのは`Hold`のときだけ、攻撃が前へ出すのは`Commit`のときだけ。両者が*同時に*位置を
触らない。すると近接が後列にいてもガタつかない — *周期的に前へ出て斬って戻る*。少し非効率なだけ
で、正常な動作だ。

**だからガタつきが起きるかどうかは、設計者ではなく*実装*が決める。** 毎フレーム争うように
組めばガタつき、状態で制御権を整理すれば正常だ。これが「遠隔が前列」(実装と無関係に設計者の
責任)との違いだ。

> このHold/Commit/Return の構造は、以前に悩んだ「トークン保持者 vs スロット配置」の問題と同じ
> 系統だ —「スロットで待ち、トークンを受け取ったら少し離れて攻撃し復帰する」というあのパターン
> の再登場だ。

#### まとめ:扱うべき対象は有限だ

「すべてを防ぐ」のではない。**「動作が破綻する場合」だけを扱い、「まずい選択」は開く。** まずい
選択は無限にあるが扱う必要がない(設計者の領分)。動作が破綻する場合は少数で(ガタつきのような
もの)、それは既にある道具(状態の分離)で整理される。扱う対象が「無限のまずい選択」ではなく
「有限の制御権の衝突」に絞られる。

## 契約の境界 — 今必ず守るべきこと

上のすべての決定を貫く、そして*今破れば後で全部直すことになる*境界が一つある。

    Group Strategy
      → slot / target / token / posture という「意図」だけを作る

    Individual AI (StateTree / GAS / 個別の戦闘ロジック)
      → その意図を、自分の状態とモンスターのパターンに合わせて「実行」へ翻訳する

グループ戦略が言ってよいことと、言ってはいけないこと:

    OK:  「お前はプレイヤーの左のスロットを担え」
         「お前は今回の攻撃トークンを受け取った」
         「お前は後列を維持しろ」

    NG:  「ゴブリンのコンボ3を再生しろ」
         「狼のジャンプ攻撃を実行しろ」
         「弓兵の特殊矢スキルを発動しろ」

**なぜ今この境界が重要か:** 契約の境界は*後で変えると上に積んだものが全部崩れる*土台だ。今、
C戦略がメンバーに「後列のスロットに立て」とだけ伝えて「どう攻撃するか」を伝えなければ → 後で
GAS ability を*その場所に*差し込めばいい。だが今、戦略が「後列でコンボ3を使え」まで伝えれば →
GASを付けるとき戦略を全部直さねばならない。

これは課題1(パターンを侵さず戦術AI)の答えでもある。契約が「意図」だけを伝えれば、新しい
モンスターの追加は*純粋に実行層の変更*だ — 新しいGAS ability + 新しいStateTreeの枝。調整層は
スロット/トークン/役割の言葉でしか話さず、特定のパターンに触れていないので、そのまま生き残る。
新しいモンスター = 修正ではなく拡張。

## まだ確定していないこと(方向だけ、実装ではない)

> 以下は「こう連携する方向」であって、実装されたものではない。現在の確定と混ぜないために
> 分けて置く。

### 役割ベースのスロット割り当て

Cの「A前列、B後列」はメンバーを役割ごとに配置する。だが既存の仲間隊形のスロット割り当ては
メンバーを*同質*に見る — 誰がどのスロットでもコスト最小で割り当てる。Cは「近接は前列スロットに
より似合い、遠隔は後列スロットにより似合う」という*気質ベースのコスト*が付くので、既存の割り当て
ロジックの拡張が要る。(役割ごとにスロットをあらかじめ分けるか、コスト行列に気質の重みを入れる
など。)これは明らかに新しい作業で、敵グループにそのまま適用するかはまだ確定しない。

### StateTree 連携

posture(グループの姿勢)と個別のモードをつなぐ実行層の候補と見ている。想定する状態:

    Approach / Hold / Commit / Return / Flee

個別のモードは `{posture, slot, token, range, HP}` から*派生*する — 戦略が「近づくか攻撃するか」を
一つひとつ細かく管理しない。ただし具体的なStateTreeの構造はまだ確定しない。

### GAS 連携

実際のスキル・攻撃パターンを実行する層として入る。**グループ戦略がGAS Abilityを直接呼ばない、
という契約の境界は維持する。** StateTreeの後の段階。

### 戦略リゾルバ

基本戦略 / スポーンプールの合成ルール / 地域の上書きを、どの順で解釈するか。現在の方向:

    1. 遭遇 / スポーンプールの合成ルール   (あれば優先)
    2. モンスターの気質に基づく基本編成     (合成が無ければこれ)

ただしこれは実装の確定ではなく、次のADRで扱う候補の構造だ。(決定1で「戦略がスポーン時点で
決まる」としたので、このリゾルバは*実行時の毎フレーム*ではなく*スポーン時に一度*動く側に近い。)

## 既存ADRとの関係

- **ADR-0002(役割の識別子 = GameplayTag)の深化だ。** モンスターの種別と戦略を切り離せば、
  役割タグをグループ戦術の層でも使える —「前列に似合う/後列に似合う」がそのタグで表現される。
- **ADR-0003(判断/実行の分離、コミットゲート)のパターンを再利用する。** Hold/Commit/Return は
  同じ問題の敵AI版だ —「常時制御ではなく、トリガー時にだけ状態を変え、その間は固定する」。
- **ADR-0005(敵グループの空間分割)と対になる。** 0005は*どのグループがスポーンされ活性化
  するか*を扱い、このADRは*活性化したグループがどの戦略を使うか*を扱う。
- **ADR-0000 概観に、敵グループ戦闘の層が追加される。**
