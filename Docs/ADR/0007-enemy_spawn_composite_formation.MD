# ADR-0007: 敵スポーンの初期配置 — 「用意した隊形を選ぶ」のをやめて、その場で組み立てた話

> このドキュメントについて：設計上の意思決定を、結論だけでなく「なぜそう決めたか」と
> 「検討して捨てた案」まで残す記録です。コードを読まなくても設計の意図と思考の流れが
> 伝わるように書いています。

* **決定時期**: 2026-06
* **対象**: 敵グループのスポーン地点ごとの初期配置を、デザイナーが直接組み立てる仕組み

---

## 概要

敵のスポーン地点ごとに、モンスターの種別と関係なく違う初期配置を作りたかった。

ありがちな作りは、「前列の一列＋後列の円」のような隊形をあらかじめ"プリセット"として用意し、
スポーン地点ではそのプリセットを選ぶ、というものだ。同じ配置を何度も使い回す前提なら、これは
正しい。だが今回はそうしなかった。

**「配置の再利用」が常に正解とは限らない、という判断がこの設計の核心だ。
敵のスポーン配置というのは、同じ並びをあちこちに同じように敷くための再利用データではなく、地点ごとに違う配置で多彩な戦闘シーンを演出すること自体がゲームの面白さに直結する領域だ。
だからここでは、再利用にこだわる必要はないと考えた。
レベルに敵を配置するのはプログラマではなく、デザイナーやプランナーだ。彼らが「この地点はこう並べたい」と思ったとき、プリセットを複製・上書きして同期を取る作業を挟まず、その場で並べ替えられるべきだ。

そこで隊形を再利用アセットにせず、スポーン地点（スポナー）の中に直接持たせ、前列・後列といった
下位の配置をその場で `＋ / −` で組み立てられるようにした。並べ方そのもの（一列・円・弧・ばらまき）
は理想的な位置を計算するだけにして、壁や経路への補正はスポナー側でまとめて行う。

このADRでは、「再利用か、その場での編集か」という分かれ道で*目的に応じてどちらを取るかを選んだ*
思考と、検討して捨てた案を記録する。

---

## 1. 一言で

> 敵スポーン地点の初期配置を、「用意したプリセットから選ぶ」のではなく、**スポナーの中で
> 下位の配置を直接 `＋ / −` で組み立てる**方式にした。各配置に敵リストと並べ方（一列・円・弧・
> ばらまき）を割り当てる。並べ方は*理想的な位置だけ*を作り、壁・障害物・経路への補正はすべて
> スポナーがまとめて担う。だから新しい並べ方を足しても補正を書き直さずに済み、デザイナーは
> スポーン地点ごとに違う配置を自由に組める。

---

## 2. なぜこの作りにしたか

### 2.1. 目標 —「エディタに置いた各スポーン地点で、その場で編集できる隊形」

具体的な場面はこうだ。

```
スポーン地点1：近接3体を前列に一列で
スポーン地点2：遠隔2体を広めにばらまいて
スポーン地点3：近接と遠隔を別々に
スポーン地点4：種別と関係なく、前列と後列を自分で指定して一つの配置に
```

ここで欲しかったのは「Cという隊形を用意して選ぶ」ことではない。レベルに置いたスポナーを開けば、
その場で下位配置を増やし、各列に何を入れるか・どう並べるかを直接決められること —— これが狙い
だった。頭の中の絵はこういう形だ。

```
スポナー
└─ 複合配置
   └─ 配置リスト
      ├─ 前列（基準位置：前へ / 並べ方：一列・円・弧・ばらまき / 敵：近接×3）
      └─ 後列（基準位置：後ろへ / 並べ方：一列・円・弧・ばらまき / 敵：遠隔×2）
```

### 2.2. 配置は強制しない —— 意図した自由度

この作りでは、近接の敵を後列に置いたり、遠隔の敵を前列に置いたりする配置を禁止しない。初期配置
の段階で「このモンスターはこの位置にいてはいけない」と強制すると、後でタンクを近接アタッカーより
前に立たせたり、遠隔の敵をあえて前進配置したりといった*演出*まで塞いでしまう。

配置がモンスターの性質と噛み合わずに起きる問題は、初期配置のデータではなく行動の層で扱う。攻めに
出て、戻り、距離を取り直し、移動のぶつかりを調整する —— それはターゲット選定・状態管理・グループ
隊形が入ってからの責任だ。（この「強制しない」考えはADR-0006の決定4と同じ系統だ。）

## 3. 決定とその理由

三つの分かれ道があった。それぞれどんな選択肢があり、なぜ今の形にしたかを順に書く。

### 3.1. 組み合わせをどこに置くか —— 再利用プリセット か スポナー内の直接編集 か

最初に思いつくのは、「一列＋一列」「一列＋円」のような組み合わせをプリセットとして用意し、スポーン
地点で*選ぶ*方式だ。

```
隊形C = 一列＋一列
隊形D = 一列＋円
隊形E = 弧＋ばらまき
```

この方式は、同じ初期配置を複数の場所で使い回すときに強い。繰り返し出てくる戦闘部屋や、特定の
モンスターセットが常に同じ形で出るゲームなら、有効な選択だ。

**だが敵の隊形は、あちこちで使い回すことより、マップ・位置・モンスターごとに自由にカスタムできる
柔軟性のほうが大事だ —— これがこの決定の核心だ。** 同じ並びを複数地点にコピーするより、地点ごとに
違う配置で多彩な演出をすること自体が面白さになる領域だから、ここでは再利用を絶対の正解とせず、
その場で手を入れられることを優先した。そして手を入れるのはデザイナーやプランナーだ。前列だけ使う
地点、後列だけ使う地点、前列の一列＋後列の円を使う地点がどれも出てくるが、この違いをプリセットの
派生や上書きで表すと、実際に編集している対象がスポナーなのかプリセットなのかが曖昧になる。

だから組み合わせをアセットに切り出さず、スポナーが直接持つデータにした。レベルに置いたスポナーを
一つ開けば、その地点の敵構成と初期配置の意図を一か所で読め、その場で直せる。（この選択のより長い
背景は4章、却下の論証は5章A。）

### 3.2. 補正を誰がやるか —— 並べ方 か スポナー か

次の分かれ道は、壁との衝突や経路への投影といった*スポーン可能な位置への補正*を誰が担うか。
「一列」「円」「弧」「ばらまき」が、点を作りながらその場で直接やる方式もありえる。

だがそうすると下位配置の責任が広がる。並べ方は「理想的にどこへ立つべきか」を計算する役割だ。実際
にその位置にスポーンできるか、壁に埋まるか、経路の上へ寄せるべきか —— それはワールドの状態を知る
スポナーが知る話だ。しかも補正を並べ方ごとに入れると、*すべての*並べ方に同じ補正が重複し、新しい
並べ方を足すたびに書き直すことになる。

だから役割をこう切った。

```
並べ方     = 理想的な配置点を計算する（ワールドの状態は知らない）
スポナー   = 実際にスポーンするとき、壁・障害物・経路への補正をまとめて担う
```

この切り分けの利点は明確だ。新しい並べ方を足す作業が*純粋に位置計算の追加*で済み、壁の補正も経路
への投影もついてくる。現在用意した並べ方は四つだ。

| 並べ方 | やること | デザイナーが触る値 |
|---|---|---|
| 一列 | 基準線に沿ってN体を一列に | 間隔、中央揃え |
| 円 | 中心から360度の円形に | 半径、開始角度、回り方、向き |
| 弧 | 指定した角度の範囲に弧状に | 半径、中心角、弧の角度、回り方、向き |
| ばらまき | 範囲内に、最小間隔を保ちつつ散らす | 範囲、最小間隔、候補数、シード、向き |

> ばらまきだけ少し特別だ。点ごとに候補を複数とって*既存の点から最も遠い*ものを選ぶ方式なので、
> 最小間隔は絶対に守る壁ではなく「これくらい離したい」という目標だ。狭ければ全部は満たせない。
> シードを固定すれば同じばらまきが再現される。

#### スポナーの補正 —— 何を保証するか

スポーン補正の責任はすべてスポナーにあり、外に約束するのは三つだ。（具体的なオプション名や探索の
半径・間隔といった値はスポナーの設定画面にすべて出ているので、そこで見て触ればいい。）

* **壁の中へ無理にスポーンさせない。** 置きたい位置がふさがっていれば周囲を少しずつ広げて空きを
  探し、設定によっては経路の上へ寄せてからスポーンを試す。最後まで安全な場所が見つからなければ
  *スポーンを諦めて*ログに残す —— 敵が壁に埋まる事故を防ぐのがこの諦めの目的だ。
* **補正の強さはデザイナーがスポーン地点ごとに調整する。** 衝突回避を効かせるか、経路の上へ寄せ
  るか、空きをどれだけ広く探すかをスポナーで決める —— コードを触らずに。
* **エディタ上ですぐ確認できる。** 設定画面のボタンでスポーンを実行して結果を見る。プレイ中で
  なければレベルに恒久的なオブジェクトを残さず（確認用の一時配置）、補正後の位置を可視化する。
  *組んで → すぐ確認 → 直す*ループがこれで回る。

### 3.3. モードをどう分けるか —— 二つの入口

スポナーは二つのモードを持つ。設定画面では、選んだモードの項目だけが見えるようにした。

* **種別ごと（ByEnemyClass）** —— いまは基本の敵リストからスポーンする*入口*。重ならないよう仮の
  位置に順に並べるだけで、近接どうしで囲む・遠隔どうしで距離を取るといった戦闘の振る舞いはまだ
  *実行しない*。後でターゲット選定・状態管理・敵グループ隊形が入ってから、同じ種別どうしの基本的な
  戦闘配置を作るための繋ぎとして空けてある。（いまここを空けておくのが意図だ —— 0006の「戦闘中の
  グループ戦略」をここに早まって入れると、役割の境界が崩れる。）
* **複合配置（CompositeFormation）** —— 3.1〜3.2の、その場で組む配置。今回の本体。

## 4. ⭐ なぜプリセットをやめたか —— より長い背景（未来の自分へ）

> 3.1で結論は書いた。ここではその結論に至るまでの*背景*を残す。後でこのコードを見て「なぜ再利用
> できるプリセットにせず、スポナーの中に全部入れたのか」と疑問に思う自分へ、「あのとき再利用は
> 良く見えたが、それが落とし穴だった」と伝えておくのが目的だ。

再利用の観点では、プリセットは確かに良く見えた。アセットをいくつか作っておいて地点ごとに選べば
いい。最初はそちらにほぼ傾いた。

だが一歩下がって*自分が実際に何をしたいのか*を見ると、ずれていた。同じ隊形を複数の場所に同じよう
に敷きたいのではなく、スポーン地点ごとにその場の地形とモンスターに合わせて*その都度違う*配置を
即席で組みたかった。プリセットにすると、地点ごとに少しずつ違う配置を作るたびに、複製・上書き・
派生・同期の問題が次々ついてくる（5章A）。再利用を得る代わりに、本当に欲しかった*その場での即時
編集*を失うことになる。

ここで整理できたのは、**「再利用」と「直接編集」は別の目標軸**だということだ。プリセットは「同じ
設定を複数の場所で」に強く、直接編集は「この場所でその都度違う形に」に強い。今回の要求は明らかに
後者だった。設計のうまさは「常に再利用する」ことではなく、*目的に応じてどちらを取るかを選べる*
ことにある。

この記録の目的はこの作りを*凍結する*ことではない。将来、同じ組み合わせを本当に複数のスポナーで
再利用したくなったら、そのときプリセットを*導入してもいい* —— ただし5章Aの上書き・同期のコストを
どう引き受けるかの答えも一緒に持ってくること。「再利用が良さそうだから」だけで戻すことだけを
防ぎたい。

## 5. 検討して捨てた案

3章で選んだ道の反対側を、なぜ取らなかったかをもう一度はっきり残す。

### 案A：再利用プリセット —— 組み合わせをアセットにして、スポーン地点で選ぶ

> 「一列＋一列」「一列＋円」のような組み合わせを別アセットにして、各スポナーはそれを*参照*して
> 配置を取ってくる。

**却下。** 再利用には強いが（3.1で認めたその強み）、今回の狙いはスポーン地点ごとの即時編集だった。
プリセットにすると次々ついてくる。

* 元のプリセットを直すと、参照している複数の地点が*まとめて*変わる。
* 一部だけ違えたいと、上書きの仕組みが要る。
* プリセットの入力とスポナー内のローカル編集をどう同期するか決めねばならない。
* 複製や派生といった付随ルールも要る。
* 結局、実際に編集している対象がスポナーなのかプリセットなのか曖昧になる。

いま必要なのは共有アセットを選ぶ流れではなく、置いたスポナーの中で完結する編集の流れだ。だから
プリセットは採らなかった。

### 案B：並べ方が壁・経路の補正まで担う —— それぞれが自分の位置に責任を持つ

> 「一列」「円」「弧」「ばらまき」が、点を作りながらその場で壁の判定・補正・経路への投影まで自分で
> やる。

**却下。** 3.2で解いたとおりだ。(1) 下位の並べ方がワールドの当たり判定や経路システムまで知る
ことになり責任が膨らむ。(2) *すべての*並べ方に同じ補正が重複し、新しい並べ方の追加コストが毎回
増える。補正をスポナーへ引き上げ、並べ方は理想位置の計算だけにした。

### 案C：実行中に自動でグループ化 —— 近くにスポーンした敵を距離でまとめて配置を決める

> スポーン後、近くにいる敵どうしを実行中に自動で一つの群れにまとめ、その群れ単位で並べ方を決める。

**却下（0006と同じ筋）。** 誰が一つの群れかを毎回距離で計算する必要があり、デザイナーが「この地点
は前列の一列＋後列の円」と*意図する*手段がなくなる。配置の意図をコードが距離で推測することになる。
ADR-0006の決定1で「グループの境界は実行中の距離ではなく配置データが作る」と決めたのと同じ理由で、
配置はデザイナーがデータで直接表す。

## 6. 得たもの／払ったもの

**得たもの：**

* **組み立ての自由度：** デザイナーはスポナーごとに前列・後列・円・弧・ばらまきを直接組める。コード
  はその入力を禁止せず、解釈して安全にスポーンする仕組みだけを担う。
* **補正の一元化：** 壁・障害物・経路への補正がスポナー一か所に集まり、新しい並べ方の追加が補正の
  重複なしに位置計算だけで済む。
* **拡張しやすさ：** 並べ方の約束（基準位置と数を受け取り、位置の並びを返す）が外に固定されている
  ので、コードのビルドなしに新しい並べ方を足せる（ADR-0002の差し替え可能な戦略の再利用）。
* **エディタで即確認：** ボタンでスポーンを実行し、確認用に一時的に置いて結果を見られるので、組んで
  ・見て・直すループが回る。
* **壁の中への無理なスポーンを避ける：** 安全な場所が見つからなければスポーンを諦めてログに残す。

**払ったもの／残した宿題：**

今回の実装は**静的なスポーン時点の初期配置まで**だ。確認したことと、まだのことを分けておく。

*静的なシーンで確認したこと：* スポナー内で下位配置を直接追加・削除／一列・円・弧・ばらまきで初期
位置を生成／各配置への敵の割り当て／壁や障害物に埋まった位置をスポナーの共通補正で周囲へずらして
スポーン／補正後の位置を基準にした可視化。

*まだ確認していないこと（動く戦闘で確かめる今後の課題）：* スポーンした敵が自分の位置を覚えて行動の
基準点にする仕組み／戦闘中にターゲットや基準点を軸に並べ直す仕組み／種別ごとの基本的なグループ
隊形（いまの「種別ごと」モードは入口だけ）／状態管理・ターゲット選定との連携／近接が後列にいるとき、
攻めに出て戻る流れ（ADR-0006の決定4）／遠隔を前列に置くような非効率な配置が実際の戦闘でどう見える
か／多数の敵が動くときの道のふさがり・移動の交差・並べ直しのコスト。

つまり今回の決定は「敵が戦闘中に賢く動く」ことではなく、**デザイナーがスポーン地点で望む初期配置を
直接作れるようになった**ところまでだ。

*補正そのものの限界：* 空き探しは、ふさがった位置の周囲をリング状に広げて探す単純な方式だ。多数の
位置が同時にふさがる狭い空間では、候補が互いの場所を侵すことがある —— 実測して気になれば、すでに
確定したスポーン位置を候補の評価に反映する形で補強する（いまは位置ごとに独立して補正している）。

## 7. 他のADRとの関係

ADR-0006は敵グループ戦闘の*上位の方向*を扱う。核心は、グループとしての戦闘方針をモンスターの種別
に固定せず、個別の気質とグループ単位の配置を切り離すことだ。

ADR-0007はその*前の段階*にあたる。戦闘中のグループ隊形ではなく、スポーン時点の初期配置をどう作る
かを扱う。

```
0006 = 戦闘中に敵グループがどんな方針で動くかの上位設計
0007 = スポーン地点で敵の初期配置をどう直接作るかの実装判断
```

0007でプリセットを捨てた理由（4章・5章A）は、0006の方向とぶつからないためでもある。スポーン時点の
初期配置と、戦闘中のターゲット・基準点に基づく判断を混ぜなければ、後でターゲット選定・状態管理・
敵グループ隊形を足すときに役割の境界が保たれる。

* **ADR-0002（差し替え可能な戦略）：** 並べ方は、その「差し替え可能な戦略」の考えを敵の配置側で
  再利用したものだ。「基準位置と数を受け取り、位置の並びを返す」という約束が外に固定されているので、
  新しい並べ方を戦略の追加だけで足せる。
* **ADR-0006（敵グループ戦闘）：** 「強制しない」（0006の決定4）と「グループの境界は配置が作る」
  （0006の決定1）を、スポーン時点の道具として先に形にしたのがこのADRだ。
