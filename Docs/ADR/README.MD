# 設計判断の記録（ADR）

> Architecture Decision Record — 「なぜそのとき、そう決めたか」を一件ずつ残す記録です。
> 結論だけでなく、検討して捨てた案とその理由まで書いています。目的は、後からその決定を
> *背景を知らないまま元に戻してしまう*ことを防ぐこと。決定を凍結するためではなく、根拠を
> 残すためのものです（根拠が変われば、堂々と直せるように）。

このフォルダは、戦闘中の仲間AI（味方キャラの立ち位置・移動・行動）をどう設計したかの
記録です。コードを読まなくても設計の意図と思考の流れが追えるように書いています。

---

## 読む順番

初めての方は **概観 → 番号順** で読むと、全体像から具体へと辿れます。

1. まず **[アーキテクチャ概観](0000-architecture_overview.MD)** で全体の層分担
   （隊形＝立ち位置の提供、ステートマシン＝行動の状態、調停役＝最終的な移動）をつかむ。
2. 次に個別の記録（0001〜0004）を番号順に。各記録は概観の枠組みの中の具体的な決定です。

## まだ開いている問い（今後の検討）

- **場面の切り替えを誰がトリガーするか** — 戦闘中、判断の主体が隊形からステートマシンへ移る、
  その切り替えを誰がどう起こすか。ステートマシンの設計の本体で扱う。（ADR-0001、概観で「どの
  システムがどの意図を出す資格を持つか」へ吸収予定。）
- **「一人ずつ」型と移動交差の最小化の関係** — 遠距離のように一人ずつ位置を出す方式で、グループ
  内の移動交差をどこまで整理するか。一人用の契約が番号どおりの対応を構造的に和らげるが、射程差が
  大きいときの整理は実測が要る。（ADR-0002）
- **複数の職が一つの配置を共有する場合** — 「近接と盾役が一つの扇形」のような要求が出たら、役割と
  グループの1対1の仮定とぶつかる。グループ分けのキーの再設計が候補。（ADR-0002）
- **再配置の猶予を、出発時ではなく到着時から数える** — 再配置の猶予が到着ではなく出発から数え
  始めるため、移動が長いと猶予が薄れる。敵が動くようになり「到着」の状態ができたら、到着のイベントを
  基準に精密化する。静止したダミーの的では影響がないため現在は見送り。（ADR-0003、概観）
- **立ち位置の周りで小さく流す（3.10）の実装** — 錨（立ち位置）は離散的に決め、その狭い周りでだけ
  小さな力場で流す「水のように流れる」挙動。行動の層が入った後、最も低い優先度の意図の一部として
  実装する。（概観 3.10、ADR-0004の捨てた案Dから分離）

## 書き方の原則（すべての記録に共通）

- **圧縮して書くと数週間後に自分が読めない。** 決定は「なぜ」を文章で書く。
- **検討して捨てた案とその理由を必ず残す。** 後でその案を再び思いついたとき「それは試して、
  こういう理由で合わなかった」とすぐ読めるように。同じ失敗の繰り返しは防ぎ、再挑戦の道は開けておく。
- **凍結ではなく根拠の保存。** 「この構造は絶対に直さない」とは書かない。根拠（現象・限界・制約）を
  残し、それが変われば堂々と直せるようにする。防ぎたいのは*背景を知らないまま元に戻すこと*だけ。
- **検証の範囲を超える断定をしない。** 「解決した」「完全に消えた」より、「改善した」「抑えやすく
  なった」のように範囲を限って書く。成果を語るときは、何が良くなったかと並べて、何はまだ解決して
  いないかも書く。
