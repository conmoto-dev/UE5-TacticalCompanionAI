# 0005. 적 그룹 공간 분할: SpatialHashGrid 채택과 그 한계

## 개요

적 그룹의 활성 판정(어떤 그룹의 AI를 돌리고, 어떤 그룹을 스폰/디스폰할지)을
매 프레임 전체 그룹 순회 없이 처리하기 위한 공간 구조를 정한다.

결론: **희소 균일 격자(Sparse Spatial Hash Grid)**. 트리 계열(BSP/KD/octree)의
적응적 분할은 도입하지 않는다. 핵심은 "이 프로젝트의 데이터 특성에 맞는 가장
단순한 구조"를 고른 것이며, 단순함은 타협이 아니라 적합성의 결과다.

---

## 문제

`UEnemyGroupSubsystem`이 그룹들의 활성 tier(교전/배회/비활성)와 스폰 여부를
판정해야 한다. 순진한 구현은 매 프레임 전체 그룹을 순회하며 거리를 재는 것이다.

    나쁜 방식:  for (전체 마커) → 거리 체크          // O(N), 확장될수록 무거움
    좋은 방식:  플레이어 주변 셀 좌표만 계산
               → 그 칸만 꺼내봄 → 후보만 거리 체크

피하고 싶었던 것은 "저장" 자체가 아니라 **"매 프레임 전체 순회"**다.
(저장은 어차피 필요하다 — 적이 어딘가 배치돼 있다는 정보는 존재해야 한다.)

## 시도한 접근과 버린 이유

### 처음 가졌던 전제: "공간 분할 = 정교한 알고리즘"

공간 분할이라는 이름에서 BSP 트리 같은 정교한 구조를 떠올렸고, 그것을 구현하는
것 자체를 목표로 삼으려 했다. 후보들을 하나씩 보며 두 가지를 깨달았다.

각 구조가 **어떻게 생겼고, 어떤 게임 상황에서 빛나는가**로 보면 선택이 명확해진다.

#### Uniform Grid — 채택
월드를 같은 크기 격자로 자르고, 각 칸이 자기 안의 객체만 들고 있는다.

    ┌────┬────┬────┐
    │ ·  │    │ ·· │   "플레이어 주변 칸"만 꺼내보면
    ├────┼────┼────┤    전체를 안 뒤져도 근처 적이 나온다
    │    │ ·  │    │
    └────┴────┴────┘

적이 맵에 고르게 흩어져 있고 위치가 거의 안 변할 때 가장 빠르고 단순하다.
→ 정적 스폰 마커 조회가 정확히 이 상황. **이걸 채택.**

#### Quadtree
칸을 고정 크기로 자르는 게 아니라, **객체가 많은 칸만 다시 4등분한다.**

    텅 빈 황야      → 큰 칸 하나로 충분
    적 100마리 도시 → 그 구역만 계속 4등분해 잘게

황야는 텅 비었는데 도시에 적이 몰린 맵이라면, 도시 쪽만 잘게 쪼개 효율을 낸다.
→ 우리 맵은 그 정도 밀도 편차가 없다. 소규모에선 트리 순회 비용이 이득보다 크다.

#### KD-Tree
점들을 축 기준으로 번갈아 반씩 갈라 트리로 만든다. **"이 지점에서 가장 가까운
적 1마리"**를 빠르게 찾는 데 특화돼 있다.
→ 우리는 "가장 가까운 1개"가 아니라 "반경 안 전부"를 찾는다. 게다가 적이 움직이면
트리 갱신이 번거롭다. 목적이 다르다.

#### BVH
객체를 감싸는 bounds(상자/구)로 묶고, **그 묶음을 다시 묶어 트리로 올린다.**

    Root Bounds
     ├ Group A Bounds
     │   ├ Actor 1
     │   └ Actor 2
     └ Group B Bounds
         ├ Actor 3
         └ Actor 4

칼이 적과 부딪혔나, 총알이 누구에게 맞나 — 부피 있는 것들의 충돌/관통 판정에 강하다.
→ 우리 마커는 "점"이다. bounds 트리는 과하다. 우리 문제는 충돌이 아니라 위치 조회다.

#### BSP
**공간을 평면으로 계속 둘로 가른다.** 어느 벽을 먼저 그릴지, 벽이 시야를 가리는지
같은 정적 레벨 구조물 처리가 본업이다 (Doom/Quake가 이걸로 렌더링 순서를 풀었다).
→ 적을 찾는 도구가 아니다. 문제 자체가 다르다.

**→ 결론:** "유명한 구조를 구현한다"가 아니라 "문제 특성에 맞는 구조를 고른다"로
목표를 재설정했다. 그 특성을 짚어보면 ↓

### 우리 데이터의 특성

- **정적** — 마커(`AEnemySpawnGroup`)는 스폰 전까지 움직이지 않는다.
- **고르게 배치 가능** — 디자이너가 직접 놓으므로 한 칸 과밀을 피할 수 있다.
- **소규모** — 맵을 넓히지 않기로 했으므로 마커 수가 폭발하지 않는다.

이 세 가지에서 Uniform Grid의 두 약점(아래 "한계")이 모두 발생하지 않는다.
그래서 가장 단순한 grid가 가장 잘 맞는다.

### Dense Grid가 아니라 Sparse Hash인 이유

같은 격자라도 저장 방식이 둘로 갈린다.

    Dense (빽빽한 배열)  TArray<TArray<Cell>>   월드 크기 고정 + 칸이 대부분 참
                                               (RTS 맵, 타일맵)
    Sparse (해시맵)      TMap<FIntPoint, ...>   월드 넓거나 빈 칸 많음
                                               ← 흩뿌린 스폰 마커

마커는 레벨에 듬성듬성 놓인다. Dense면 텅 빈 칸까지 배열로 들어 낭비다.
빈 칸은 키 자체가 없는 `TMap` 쪽이 맞다.

## 최종 결정: Sparse Spatial Hash Grid

```cpp
TMap<FIntPoint, TArray<TWeakObjectPtr<AEnemySpawnGroup>>> MarkerGrid;
```

월드 좌표를 셀 좌표로 바꿔 칸에 넣는다. 핵심은 조회가 **순회가 아니라 직접 접근**
이라는 점이다 — 주변 반경이 닿는 칸 좌표를 직접 계산해 그 키만 `Find`한다.

```cpp
FIntPoint ToCell(const FVector& P) const
{
    return FIntPoint(FMath::FloorToInt(P.X / CellSize),
                     FMath::FloorToInt(P.Y / CellSize));
}
// 쿼리: 플레이어 칸 주변 R칸만 — 전체 Cells 순회가 아님
for (int32 dx = -R; dx <= R; ++dx)
for (int32 dy = -R; dy <= R; ++dy)
    if (auto* Bucket = MarkerGrid.Find(PlayerCell + FIntPoint(dx, dy)))
        { /* 이 칸의 마커만 후보 → narrow-phase 거리 검사 */ }
```

이것이 "말만 공간 분할"과 진짜 공간 분할을 가르는 지점이다.
`for (auto& Pair : Cells)`(전체 순회)가 아니라 `Cells.Find(특정좌표)`(직접 접근)다.

### 비용을 더 줄이는 두 장치

- **이동 게이트:** 플레이어가 임계 이하로만 움직였으면 판정 자체를 건너뛴다.
  "매 프레임"을 "몇 미터 움직일 때마다"로 바꾼다.
- **경계 감지의 역전:** "어떤 그룹이 반경에 들어왔나"를 그룹 쪽에서 찾지 않는다.
  플레이어의 이웃 칸을 다시 조회하면, 경계 진입은 그 쿼리의 부산물로 자동으로 나온다.
  (플레이어는 하나뿐이라 재버킷이 사실상 공짜.)

### 히스테리시스는 셀이 아니라 거리 밴드에

tier 전이 떨림 방지는 셀 경계가 아니라 거리 밴드에 건다 (활성 반경 < 비활성 반경,
예: 활성 2000 / 비활성 2400). 셀 경계에 걸면 복잡해진다 — 셀은 후보를 거르는
용도일 뿐, tier 판정의 기준이 아니다.

### 초기값 (출발점, 확정 아님)

    SpawnRadius   = 4000      # 이 반경 진입 시 스폰 + record 등록
    EngageRadius  = 1600      # 이 반경 진입 시 AI tier 교전으로
    CellSize      = 1600~2000 # ≈ EngageRadius, 또는 SpawnRadius / 2

CellSize는 EngageRadius 근처 또는 SpawnRadius의 절반을 출발점으로 잡았다.
플레이테스트로 조정될 값이다 (아래 "약점 1"의 셀 크기 튜닝이 여기 해당).

## 배운 것: 공간 분할에 완벽한 이론은 없다

이 작업의 가장 큰 수확은, 공간 분할에 가졌던 환상을 버린 것이다. 어떤 단일 구조도
모든 상황을 완벽히 푸는 "정답"이 아니다.

### 약점 1: 셀 크기를 잘못 잡으면 (density skew)

칸 하나가 커버하는 범위를 잘못 잡으면 이렇게 무너진다.

- **칸이 너무 크면:** 보스방 입구처럼 적이 한곳에 모인 구역에서 그 적들이 전부
  같은 칸에 들어간다 → 결국 그 칸 안에서 다시 전부 거리 계산. grid 쓴 의미가 없어진다.
- **칸이 너무 작으면:** 플레이어 주변 4000 반경을 보는데 칸이 500이면 16×16=256칸을
  일일이 뒤져야 한다 → 주변 칸 순회가 오히려 늘어난다.

Quadtree는 몰린 칸만 더 쪼개 이를 완화한다. 단 그 적응성은 "적 수만 마리 +
극단적 밀도 편차"에서 값을 한다.
→ 우리: 디자이너가 직접 분산 배치해 회피. **단 이건 "해결"이 아니라 "이 규모에서
회피 가능"이다 — 규모가 커지면 다시 마주친다.**

### 약점 2: 움직이는 적의 재계산 (rebucketing)

    적이 칸 A → 칸 B로 이동
    → 칸 A bucket에서 제거 → 칸 B bucket에 삽입

적이 칸 경계를 넘을 때마다 이 갱신이 필요하다. 빠르게 움직이는 적이 많으면 이 비용이
매 프레임 쌓인다. 어떤 구조든 "움직이는 대상을 공간 구조에 반영하는" 문제에서
자유롭지 않다 — 갱신 빈도와 정확도 사이의 트레이드오프가 남는다.
→ 우리: 마커는 정적이라 재버킷이 BeginPlay 1회뿐. 배회 그룹의 저빈도 모션도 낮은
tick에서만 위치를 갱신해 비용이 분산된다. **역시 "회피"이지 "해결"이 아니다.**

### 정리한 인식

- 공간 분할은 "정교할수록 좋다"가 아니다. 분포가 고르고 정적이면 가장 단순한 grid가
  가장 빠르다 (캐시 친화적, 분기 없음).
- 트리 계열의 적응성·동적 대응은 공짜가 아니다 — 순회 비용, 구현 복잡도, 균형 깨짐이
  대가다. 그 대가가 정당한 규모가 따로 있다.
- 완벽한 단일 이론은 없다. "내 데이터가 어떤 분포·동적 특성을 갖나"에 맞춰 고르는
  것이 전부다. 환상은 "정답 구조가 있다"는 믿음이었다.

## 남은 한계 / 미래 방향

#### 마커가 수백을 크게 넘거나 맵을 확장하면
셀 크기 튜닝(약점 1)이 다시 쟁점이 된다. 선택지를 복잡도 순으로:
CellSize 재튜닝 → 계층 해시 grid → quadtree.
**측정으로 병목이 입증되기 전엔 올리지 않는다 (YAGNI).**

#### encounter 반경이 크게 다양해지면 — 계층 해시 grid
적 그룹마다 활동 반경이 크게 다를 때 단일 CellSize로는 양극단 처리가 애매해진다.

    작은 슬라임 무리   반경 300
    큰 캠프           반경 3000
    월드 보스 영역     반경 10000

작은 칸에 맞추면 보스 영역이 수많은 칸에 걸치고, 큰 칸에 맞추면 슬라임들이 한 칸에
우르르 몰린다. 계층 해시 grid는 여러 레벨(예: CellSize 500/1000/2000/4000)을 두고
객체 크기에 맞는 레벨에 넣어 푼다. (UE의 `THierarchicalHashGrid2D`가 이 방식.)
→ 일반 몹 / 정예 캠프 / 원거리 초소 / 보스 아레나가 한 맵에 공존하면 그때 고려.

#### 움직이는 적이 본격 도입되면
재버킷 빈도가 오른다(약점 2). 현재는 정적 전제라 유예된 문제이며, 그 시점에 갱신
빈도/정확도 트레이드오프를 다시 설계한다.

## 기존 ADR과의 관계

- 이 결정은 `UEnemyGroupSubsystem`(별도 ADR)의 활성 판정 메커니즘을 구체화한다.
- 공간 구조는 "스폰된 그룹 중 근처 찾기"만 담당한다. 메모리 로드/언로드(스트리밍)는
  이 프로젝트 범위 밖이며 WorldPartition도 쓰지 않는다 — 그 경계는 그룹 스폰 정책
  ADR에서 다룬다. (참고: WorldPartition도 큰 단위에서는 런타임 grid로 월드를 나눠
  streaming source 주변 칸을 load/unload한다. 우리가 직접 만드는 건 그보다 작은,
  런타임 AI 후보 조회용 grid다.)
