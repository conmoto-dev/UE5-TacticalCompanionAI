# ADR-0007: 적 스폰 Composite Formation — SubFormation을 Spawner 안에서 직접 조합한다

> 작성 원칙 (README_ko·ADR-0001과 동일): 압축해서 적으면 몇 주 뒤에 내가 못 읽는다.
> 결정은 "왜"를 문장으로 풀어쓴다. 단, 변수명·내부 함수명 같은 구현 디테일은 적지 않는다 —
> 그건 코드를 열면 늘 최신으로 거기 있고, 문서에 박으면 리팩토링하는 순간 거짓말이 된다.
> 이 문서가 가리키는 건 "어느 클래스가 무슨 책임을 지는가"까지다. 나머지는 코드가 말한다.

- **결정일**: 2026-06
- **관련 코드 (길 찾기용 앵커)**:
  - `AEnemySpawner` (`Enemies/Spawning/`) — 스폰 입구, 모드 분기, 스폰 보정을 *공통으로* 처리
  - `UEnemySubFormationBase` + `_Line` / `_Circle` / `_Arc` / `_Scatter`
    (`Enemies/Formation/`) — 교체 가능한 슬롯 생성 전략. 계약은 `BuildSlots` 하나
  - `FEnemyCompositeFormation` / `FEnemySubFormation` (`Enemies/Formation/EnemyFormationTypes.h`)
    — Spawner 안에 인라인으로 들어가는 배치 데이터
  - `EEnemyFormationMode { ByEnemyClass, CompositeFormation }` — 배치 모드
- **선행 결정**:
  - ADR-0006 (적 그룹 전투 아키텍처 — 이 ADR은 그 **전 단계**다. 0006은 *전투 중* 그룹이
    어떤 방침으로 움직이나, 0007은 *스폰 시점*의 초기 배치를 어떻게 작성하나. §7 관계 참조.
    **0006의 구현이 아니다.**)
  - ADR-0002 (전략 객체 추상화 — `UEnemySubFormationBase`는 그 "교체 가능한 전략" 패턴을
    적 배치 쪽에서 재사용한다)

---

## 1. 한 줄 요약

> 적 스폰 지점의 초기 배치를, "미리 만들어둔 Formation Preset을 고르는" 방식이 아니라,
> **레벨에 놓인 Spawner 안에서 하위 배치(전열·후열 등)를 `+ / -`로 직접 조합하는** 방식으로
> 만든다. 각 칸에 적 목록과 배치 형태(`Line` / `Circle` / `Arc` / `Scatter`)를 직접 할당한다.
> 배치 형태는 *이상적인 슬롯 위치만* 계산하고, 벽·장애물·NavMesh 보정은 전부 Spawner가
> 공통으로 처리한다. 그래서 새 배치 형태를 추가해도 보정 코드를 다시 짤 필요가 없고,
> 디자이너는 Spawner마다 다른 배치를 자유롭게 조합할 수 있다.

## 2. 맥락 (왜 이 결정이 필요했나)

### 2.1. 목표 — "에디터에 배치한 각 스폰 지점에서 바로 편집되는 진형"

적 스폰 지점마다 몬스터 종류와 무관하게 다른 초기 배치를 만들고 싶었다. 구체적인 장면:

```
스폰 지점 1: 근접 3마리를 전열 Line으로
스폰 지점 2: 원거리 2마리를 넓게 Scatter
스폰 지점 3: 근접과 원거리를 따로 배치
스폰 지점 4: 종류 무관하게, 전열과 후열을 직접 지정해 하나의 배치로
```

여기서 내가 원한 핵심은 **"C라는 진형을 미리 만들어두고 고른다"가 아니었다.**
적 진형은 이곳저곳에서 반복 사용하는 것보다, 맵·위치·몬스터마다 자유롭게 커스텀할
수 있는 유연성이 더 중요하다 — 이게 이 결정의 핵심 포인트.
목표는 레벨에 놓인 Spawner를 열면 그 자리에서 하위 배치를 추가하고, 각 칸에 어떤 적을 넣을지·어떤
배치 형태를 쓸지 바로 정하는 것이었다. 머릿속 그림은 이런 트리다.

```
AEnemySpawner
└─ CompositeFormation
   └─ SubFormations
      ├─ 前列 (전열)
      │  ├─ 로컬 위치/회전 = Spawner 기준 오프셋
      │  ├─ 배치 형태      = Line / Circle / Arc / Scatter
      │  └─ 적 목록        = 근접 ×3
      └─ 後列 (후열)
         ├─ 로컬 위치/회전 = Spawner 기준 오프셋
         ├─ 배치 형태      = Line / Circle / Arc / Scatter
         └─ 적 목록        = 원거리 ×2
```

### 2.2. 배치는 강제하지 않는다 — 의도된 자유도

이 구조에서는 근접형 적을 후열에 두거나, 원거리형 적을 전열에 두는 배치를 금지하지 않는다.
초기 배치 단계에서 "이 몬스터는 이 위치에 있으면 안 된다"를 강제하면, 나중에 탱커가 근접
딜러보다 앞에 서거나 원거리 적이 의도적으로 전진 배치되는 식의 연출을 막게 된다.

배치가 몬스터 성향과 맞지 않아 생기는 문제는, 초기 배치 데이터가 아니라 행동 계층에서
다룬다. 공격하러 나가고, 돌아오고, 거리를 다시 잡고, 이동 충돌을 조정하는 일은 Targeting /
StateTree / Group Formation 이후의 책임이다. (이 "강제하지 않음"은 ADR-0006 결정 4와 같은
계열이다.)

## 3. 결정과 그 이유

세 갈래에서 길이 갈렸다. 각각 어떤 선택지가 있었고, 왜 지금 구조로 갔는지 순서대로 적는다.

### 3.1. 조합을 어디에 둘까 — Preset 자산 vs Spawner 인라인

먼저 떠오른 건 `Line + Line`, `Line + Circle` 같은 조합을 Profile이나 Preset 자산으로
만들어두고 스폰 지점에서 *고르는* 방식이다.

```
Formation C = Line + Line
Formation D = Line + Circle
Formation E = Arc + Scatter
```

이 방식은 같은 초기 배치를 여러 곳에서 재사용할 때 강하다. 반복되는 전투방 배치나, 특정
몬스터 세트가 항상 같은 형태로 나오는 게임이라면 유효한 선택이다.

**하지만 적 진형은 이곳저곳에서 반복 사용하는 것보다, 맵·위치·몬스터마다 자유롭게 커스텀할
수 있는 유연성이 더 중요하다 — 이게 이 결정의 핵심 포인트다.** 몬스터 진형이라는 건 같은
형태를 여러 곳에 재사용하는 자산이라기보다, 에디터에 배치해둔 스폰 지점에서 *즉각 손볼 수
있어야 하는* 연출에 가깝다고 봤다. 전열만 쓰는 지점, 후열만 쓰는 지점, 전열 Line + 후열
Circle을 쓰는 지점이 다 생기는데, 이 차이를 Profile 파생이나 Override로 표현하면 실제
편집 대상이 Spawner인지 Profile인지 흐려진다.

그래서 조합을 자산으로 빼지 않고, Spawner가 직접 들고 있는 인라인 데이터로 뒀다. 레벨에 놓인
Spawner 하나만 열면, 그 지점의 적 구성과 초기 배치 의도를 한곳에서 읽고 그 자리에서 고칠 수
있다. (이 선택의 더 긴 맥락은 §4, 기각 논증은 §5-A.)

### 3.2. 보정을 누가 할까 — 배치 형태 vs Spawner

다음 갈림길은 벽 충돌이나 NavMesh 투영 같은 *스폰 가능 위치 보정*을 누가 맡느냐다. `Line` /
`Circle` / `Arc` / `Scatter`가 슬롯을 만들면서 그 자리에서 직접 처리하는 방식도 가능하다.

하지만 그렇게 하면 하위 배치 구현의 책임이 넓어진다. 배치 형태는 "이상적으로 어디에 서야
하는가"를 계산하는 역할이다. 실제로 그 위치에 스폰 가능한지, 벽에 묻히는지, NavMesh 위로
옮겨야 하는지는 월드 상태를 아는 Spawner가 아는 일이다. 게다가 보정을 배치 형태마다 넣으면,
*모든* 형태에 같은 보정 코드가 반복된다 — 새 형태를 추가할 때마다 보정을 다시 짜야 한다.

그래서 책임을 이렇게 잘랐다.

```
배치 형태 (UEnemySubFormationBase 파생)   = 이상적인 슬롯 위치 계산 (월드 상태 모름)
Spawner   (AEnemySpawner)                = 실제 스폰 시 벽/장애물/NavMesh 보정을 공통 처리
```

이 분리의 이득은 명확하다. 새 배치 형태를 추가하는 일이 *순수하게 위치 계산 추가*로 끝나고,
벽 보정과 NavMesh 투영은 공짜로 따라온다.

배치 형태가 외부에 약속하는 계약은 하나다 — **`BuildSlots`: 기준 위치와 슬롯 수를 받아,
이상적인 슬롯 배열을 돌려준다.** 이게 `BlueprintNativeEvent`라 C++로도 BP로도 새 형태를
추가할 수 있다(ADR-0002의 전략 패턴 재사용). 현재 구현된 네 가지는 이렇다.

| 배치 형태 | 하는 일 | 디자이너가 만지는 값 |
|---|---|---|
| `Line` | 기준선을 따라 N명 일렬 | Slot Spacing, Center Aligned |
| `Circle` | 중심 기준 360도 원형 | Radius, Start Angle, Clockwise, Facing Mode |
| `Arc` | 지정 각도 범위 안에 호 형태 | Radius, Center Angle, Arc Angle, Clockwise, Facing Mode |
| `Scatter` | 반경 안에서 최소 거리 기반 흩뿌림 | Scatter Radius, Min Distance, Candidate Count, Seed, Facing Mode |

> Scatter만 살짝 특별하다. 슬롯마다 후보를 여러 개 뽑아 *기존 슬롯과 가장 멀리 떨어지는*
> 후보를 고르는 방식이라(best-candidate sampling), Min Distance는 절대 지켜야 하는 벽이
> 아니라 "이만큼 떨어뜨리고 싶다"는 목표다. 좁으면 다 못 채울 수 있다. Seed를 고정하면 같은
> 흩뿌림이 재현된다.

#### Spawner의 보정 — 무엇을 보장하나

스폰 보정의 책임은 전부 Spawner에 있고, 외부에 약속하는 건 세 가지다. (구체적인 옵션 이름과
탐색 반경·간격 같은 값은 Spawner의 Details에 다 노출돼 있으니, 거기서 보고 만지면 된다.)

- **벽 안에 강제로 박지 않는다.** 원하는 슬롯이 막혀 있으면 주변을 조금씩 넓혀가며 빈자리를
  찾고, 옵션에 따라 NavMesh 위로 끌어온 뒤 스폰을 시도한다. 끝내 안전한 자리를 못 찾으면
  *스폰을 포기*하고 실패 로그를 남긴다 — 적이 벽에 끼는 사고를 막는 게 이 포기의 목적이다.
- **보정 강도는 디자이너가 스폰 지점마다 튜닝한다.** 충돌 해소를 켤지, NavMesh 위로 끌어올지,
  빈자리를 얼마나 넓게 찾을지를 Spawner에서 정한다 — 코드 수정 없이.
- **에디터에서 바로 확인된다.** Details 버튼으로 스폰을 돌려 결과를 본다. 게임 플레이 중이
  아니면 레벨에 영구 오브젝트를 남기지 않고(임시 스폰), 보정된 위치를 디버그로 표시한다.
  *조합 → 즉시 확인 → 조정* 루프가 이 덕에 성립한다.

### 3.3. 모드를 어떻게 나눌까 — 두 입구

Spawner는 두 가지 모드를 가진다. Details에서는 선택한 모드의 데이터만 보이게 했다.

```
EEnemyFormationMode
├─ ByEnemyClass        → 단일 적 목록 사용
└─ CompositeFormation  → 하위 배치 조합 사용
```

- **`ByEnemyClass`** — 현재는 기본 적 목록으로 스폰하는 *입구*다. 겹치지 않을 임시 일렬
  슬롯에 입력 순서대로 배치할 뿐, 아직 근접끼리 포위하거나 원거리끼리 거리 유지하는 전투
  행동은 *실행하지 않는다.* 이 모드는 나중에 Targeting / StateTree / EnemyGroupFormation이
  들어온 뒤, 같은 EnemyClass끼리 기본 전투 배치를 만들기 위한 연결점으로 비워둔 것이다.
  (지금 비워두는 게 의도다 — 0006의 "전투 중 그룹 전략"을 여기 섣불리 채우면 책임 경계가
  무너진다.)
- **`CompositeFormation`** — §3.1~3.2의 인라인 조합. 이번 구현의 본체다.

## 4. ⭐ 왜 Preset을 버렸나 — 더 긴 맥락 (미래의 나에게)

> §3.1에서 결론은 적었다. 여기선 그 결론에 이르기까지의 *맥락*을 남긴다. 미래에 이 코드를
> 보고 "왜 재사용 가능한 Preset 자산으로 안 빼고 Spawner 안에 다 넣었지?"라고 의아해할
> 나에게, "그때 재사용이 좋아 보였지만 그게 함정이었다"를 일러두는 게 목적이다.

재사용 관점에선 Preset이 분명 좋아 보였다. 깔끔하게 자산 몇 개 만들어두고 스폰 지점마다
고르면 되니까. 처음엔 그쪽으로 거의 기울었다.

하지만 한 발 물러서서 *내가 실제로 뭘 하고 싶은가*를 보니 어긋났다. 나는 같은 진형을 여러
곳에 똑같이 깔고 싶은 게 아니라, 스폰 지점마다 그 자리의 지형과 몬스터에 맞춰 *그때그때 다른*
배치를 즉석에서 짜고 싶었다. Preset으로 가면, 지점마다 조금씩 다른 배치를 만들 때마다 Profile
복제·Override·Variant·동기화 문제가 줄줄이 따라온다(§5-A). 재사용을 얻는 대신, 내가 정작
원한 *그 자리에서의 즉각 편집*을 잃는 거였다.

여기서 정리된 건 **"재사용"과 "직접 편집"이 서로 다른 목표축**이라는 거다. Preset은 "같은
설정을 여러 곳에서"에 강하고, 인라인은 "이 자리에서 그때그때 다르게"에 강하다. 이번 요구는
명백히 후자였다.

이 기록의 목적은 인라인 구조를 *동결*하는 게 아니다. 미래에 같은 조합을 정말 여러 Spawner
에서 재사용하고 싶어지면, 그때 Preset을 *도입해도 된다* — 다만 그땐 §5-A의 Override·동기화
비용을 어떻게 감당할지 답을 같이 가져와야 한다. "재사용이 좋아 보이니까"만으로 되돌리는 것만
막으면 된다.

## 5. 기각한 대안

§3에서 고른 길의 반대편을, 왜 안 골랐는지 한 번 더 명확히 박아둔다.

### 대안 A: Formation Profile / Preset 자산 — 조합을 자산으로 만들고 스폰 지점에서 고르기

> `Line + Line`, `Line + Circle` 같은 조합을 별도 자산으로 만들어두고, 각 Spawner는 그
> 자산을 *참조*해서 배치를 가져온다.

**기각.** 재사용에는 강하지만(§3.1에서 인정한 그 강점), 이번 목표는 스폰 지점별 즉각
편집이었다. Profile을 쓰면 줄줄이 딸려온다.

- 원본 Profile을 수정하면 그걸 참조하는 여러 스폰 지점이 *함께* 바뀐다.
- 스폰 지점에서 일부만 다르게 하고 싶으면 Override 규칙이 필요해진다.
- Profile의 입력과 Spawner 안의 로컬 편집 내용을 어떻게 동기화할지 정해야 한다.
- Copy From Profile, Variant 같은 부가 정책이 필요해진다.
- 결국 실제 편집 대상이 Spawner인지 Profile인지 흐려진다.

지금 필요한 건 공유 자산을 고르는 흐름이 아니라, 배치된 Spawner 안에서 완결되는 편집
흐름이다. 그래서 Profile / Preset은 채택하지 않았다.

### 대안 B: 배치 형태가 벽/NavMesh 보정까지 처리 — 각 형태가 자기 슬롯을 책임지기

> `Line` / `Circle` / `Arc` / `Scatter`가 슬롯을 만들면서 그 자리에서 벽 체크·충돌 보정·
> NavMesh 투영까지 직접 한다.

**기각.** §3.2에서 푼 그대로다. (1) 하위 배치 형태가 월드 충돌과 NavSystem까지 알아야 해서
책임이 커지고, (2) *모든* 형태에 같은 보정 코드가 반복돼 새 형태 추가 비용이 매번 늘어난다.
보정을 Spawner로 끌어올려, 배치 형태는 이상적 위치 계산만 하게 했다.

### 대안 C: 런타임 자동 그룹핑 — 가까이 스폰된 적을 거리로 묶어 배치 결정

> 스폰 후 가까이 있는 적들을 런타임에 자동으로 한 무리로 묶고, 그 무리 단위로 배치 형태를
> 정한다.

**기각(0006과 같은 결로).** 누가 한 무리인지 매번 거리로 계산해야 하고, 디자이너가 "이
지점은 전열 Line + 후열 Circle"을 *의도*할 방법이 없다. 배치 의도를 코드가 거리로 추측하게
만드는 셈이다. ADR-0006 결정 1에서 "그룹 경계는 런타임 거리가 아니라 배치 데이터가
만든다"고 정한 것과 같은 이유로, 배치는 디자이너가 데이터로 직접 표현한다.

## 6. 결과 (얻는 것 / 치르는 것)

**얻는 것:**

- **작성 자유도:** 디자이너는 Spawner마다 전열/후열/원형/호/흩뿌림을 직접 조합한다. 코드는
  그 입력을 금지하지 않고, 해석해서 안전하게 스폰하는 mechanism만 담당한다.
- **보정 단일화:** 벽·장애물·NavMesh 보정이 Spawner 한 곳에 모여, 새 배치 형태 추가가 보정
  코드 중복 없이 위치 계산 추가만으로 끝난다.
- **BP 확장 가능:** `BuildSlots` 계약 덕에 C++ 빌드 없이 BP로 새 배치 형태를 추가할 수 있다.
- **에디터 즉시 확인:** Details 버튼 스폰 + 임시 프리뷰 + 슬롯 디버그 표시로, 배치를
  조합하고 바로 결과를 보는 루프가 성립한다.
- **벽 안 강제 스폰 회피:** 안전한 자리를 못 찾으면 스폰을 포기하고 로그를 남긴다.

**치르는 것 / 남은 숙제:**

이번 구현은 **정적 스폰 시점의 초기 배치**까지다. 검증한 것과 아직 아닌 것을 분리해 둔다.

*정적 씬에서 검증한 것:*
- Spawner 안에서 하위 배치를 직접 추가/삭제
- `Line` / `Circle` / `Arc` / `Scatter`로 초기 슬롯 생성
- 각 칸별 적 목록 할당
- 벽/장애물에 박힌 슬롯을 Spawner 공통 보정으로 주변 위치에 스폰
- 보정된 위치 기준 디버그 표시

*아직 검증하지 않은 것 (동적 전투에서 확인할 미래 과제):*
- 스폰된 적이 자기 슬롯을 기억하고 행동 기준점(닻)으로 쓰는 구조
- 전투 중 Target / Anchor를 기준으로 재배치하는 구조
- EnemyClass별 기본 Group Formation (현재 `ByEnemyClass`는 입구만)
- StateTree와 Targeting 연동
- 근접이 후열에 있을 때 나갔다 돌아오는 Hold / Commit / Return 흐름 (ADR-0006 결정 4)
- 원거리 전열 배치 같은 비효율적 배치가 실제 전투에서 어떻게 보이는지
- 다수 적이 움직일 때 길막힘·이동 교차·재배치 비용

즉 이번 결정은 "적이 전투 중 똑똑하게 움직인다"가 아니라, **디자이너가 스폰 지점에서 원하는
초기 배치를 직접 만들 수 있게 된 것**까지다.

*보정 로직 자체의 한계:*
- 빈자리 탐색은 막힌 슬롯 주변을 링 모양으로 넓혀가며 찾는 단순한 방식이다. 다수 슬롯이
  동시에 막히는 좁은 공간에서는 후보가 서로의 자리를 침범할 수 있다 — 실측 후 거슬리면 이미
  확정된 스폰 위치를 후보 평가에 반영하는 식으로 보강한다 (현재는 슬롯별 독립 보정).

## 7. 기존 ADR과의 관계

ADR-0006은 적 그룹 전투 아키텍처의 *상위 방향*을 다룬다. 핵심은 그룹 전투 방침을 몬스터
종류에 고정하지 않고, 개별 기질과 그룹 단위 배치를 분리한다는 것이다.

ADR-0007은 그 *전 단계*다. 전투 중 Group Formation이 아니라, 스폰 시점의 초기 배치를 어떻게
작성할지 다룬다.

```
0006 = 전투 중 적 그룹이 어떤 방침으로 움직일지에 대한 상위 설계
0007 = 스폰 지점에서 적 초기 배치를 어떻게 직접 작성할지에 대한 구현 결정
```

0007에서 Preset을 버린 이유(§4, §5-A)는 0006의 방향과 충돌하지 않기 위해서이기도 하다.
스폰 시점의 초기 배치와 전투 중 Target/Anchor 기반 판단을 섞지 않으면, 이후 Targeting·
StateTree·EnemyGroupFormation을 붙일 때 책임 경계가 유지된다.

- **ADR-0002 (전략 객체 추상화):** `UEnemySubFormationBase`는 그 "교체 가능한 전략" 패턴을
  적 배치 쪽에서 재사용한다. `BuildSlots` 계약이 외부에 고정돼 있어, 새 배치 형태를 전략
  추가만으로 넣을 수 있다 (OCP).
- **ADR-0006 (적 그룹 전투):** "강제하지 않음"(0006 결정 4)과 "그룹 경계는 배치가
  만든다"(0006 결정 1)를 스폰 시점 도구로 먼저 구현한 것이 이 ADR이다.
- 이번 결정으로 얻은 것은 재사용 Preset이 아니라 **작성 자유도**다. 코드는 배치를 해석하고
  안전하게 스폰하는 mechanism만 담당하고, 무엇을 어떻게 배치할지는 디자이너에게 연다.
