# UE5 Tactical Companion AI

> Unreal Engine 5 / C++ で開発している、3人の仲間とフィールドを移動し、そのまま戦闘へ移行するための仲間AIシステムです。  
> 『グランブルーファンタジー リリンク』『アークナイツ：エンドフィールド』のように、仲間が集団として自然に見えながら、戦闘では各自が状況を判断して動くことを目指しています。

実装そのものだけでなく、**プログラマが用意した判断材料をプランナー／ゲームデザイナーが組み合わせ、コンテンツごとのAIへ展開できる構造**を重視しています。

## ✨ 実装済みの機能

### 非戦闘時の追従・環境適応

- **パーティ単位の管理** — PartyManager / AIController / Characterに責務を分け、特定のキャラクターにパーティ全体の寿命を持たせない構成
- **データ駆動の隊形** — DataAssetで隊形を定義し、コードを再ビルドせずに追加・調整可能
- **V字 ↔ I字の自動切り替え** — 通路幅に応じて隊形を変更し、ヒステリシスで頻繁な切り替えを抑制
- **地形に沿った配置補正** — NavMesh投影、傾斜への高さ補正、壁沿いの補正を共通パイプラインとして処理
- **速度に応じた間隔と遅延回転** — リーダーの移動に対して隊形が硬く追従せず、速度と向きの変化を滑らかに反映
- **停止時のスロット再割り当て** — 移動の交差が少なくなるようメンバーとスロットを再対応付け
- **プレイヤーへの「譲り」** — 隊形全体が共有状況を見て左右を割り当て、全員が同じ場所へ避ける問題を防止
- **Detour Crowdによる群衆回避** — Controllerを入口にLeader / Normal / Yieldingの回避役割を設定
- **上り段差のトラバーサル** — 壁の検知、踏み切り位置、進入操作、放物線ジャンプまでを分離して実装

### 敵のスポーンとグループ管理

- **スポーン地点ごとの複合配置** — Line / Circle / Arc / ScatterをSpawner内で直接組み合わせ、前列・後列などをその場で編集
- **配置ロジックの差し替え** — 下位配置をStrategyとして実装し、新しい並べ方をBlueprintから追加可能
- **理想位置とワールド補正の分離** — Strategyは理想的な配置点だけを生成し、壁・障害物・NavMeshへの補正はSpawnerが共通処理
- **エディタ上の確認ループ** — 設定画面から一時的にスポーンし、配置を作る・見る・直す流れを短縮
- **ランタイムの`AEnemyGroup`** — Spawnerは生成とメンバー登録までを担当し、その後の名簿・状態・全滅判定の責務はグループへ移譲
- **グループ単位の知覚** — 敵を1体発見すると所属グループ全体を候補に加え、配置時に決めたグループ境界を実行時にも利用
- **知覚と交戦の分離** — パーティ側の認知と敵側のIdle / Alert / Engaged / Returnを独立させ、片方だけが相手を認識している状況も表現可能

### キャラクターごとのターゲット選定

- **重み付きターゲットポリシー** — Nearest / NearestLeader / LeaderFocus / AllyFocusなど、0〜1の点数を返す小さなポリシーをキャラクターごとに組み合わせる構成
- **中央からの強制割り当てを行わない** — 集中攻撃や分散は、各キャラクターのポリシーと重みから生まれる結果として表現
- **陣営共通の評価ループ** — 共通Selectorが評価・確定・寿命管理を持ち、味方／敵の違いは候補とコンテキストの供給箇所だけに限定
- **ずれた再評価タイミング** — 全員が同じフレームでターゲットを変える機械的な動きを避けるため、評価周期とターゲット喪失時の反応を個体ごとにずらす
- **ポリシーごとのHold** — 実測で確認したターゲットの往復を、点数差の閾値ではなく「その判断をどれだけ信頼するか」という時間で抑制
- **ステートレスなポリシー** — 実行時の状態はSelector Componentが持ち、ポリシーは設定と計算だけを担当。将来はGAS Abilityから発動時に一度だけ問い合わせる用途にも再利用可能

### 個別ターゲットに基づく戦闘位置

- **メンバーごとのターゲットとHome** — 各メンバーが自分のSelectorの結果を使い、役割と射程に応じた戦闘上の基準位置を確定
- **近接のEncircle** — ターゲットへの進入方向を基本角度とし、すでに確定している仲間と重なる場合だけ新しく入る側を調整
- **遠距離のRangedSafe** — ターゲット周囲360度の候補を、射程・脅威・占有・味方への寄りで評価
- **全Strategyを「1人 → 1地点」に統一** — 一人のターゲット変更が他メンバー全員の再配置へ伝播しない構成
- **コミットゲート** — 毎フレーム最適位置を送り直さず、射程外や脅威接近など、現在の位置を捨てる理由が生じたときだけ再評価
- **共通の地形補正と移動実行** — Strategyが出した位置を共通処理でNavMeshと地形へ補正し、実際の移動はAIControllerへ委譲

### Home周辺の戦闘待機行動

- **Homeを固定スロットとして扱わない** — 攻撃や回避がないときに戻る基準点として保持
- **ターゲットを注視しながら微移動** — Home周辺で左右方向への短い移動と待機を繰り返し、棒立ちを軽減
- **既存のMoveToを常に優先** — PathFollowingが動いている間は即座に譲り、FormationやTraversal側にMicro Movementの知識を持たせない
- **攻撃システムとの接続点** — 攻撃中に微移動を停止する`SetSuppressed`を用意

## 🎯 設計上の主な判断

ここでは、クラスの責務、依存方向、他職種との連携、ゲーム体験への展開について、特に重視している判断をまとめます。実装上の細部、検討して捨てた案、残っている制約は **[`Docs/ADR/`](./Docs/ADR/)** に記録しています。

### 1. 状態の所有者を一つにし、依存を一方向にする

パーティのメンバーとモードは`APartyManager`、敵グループの名簿と状態は`AEnemyGroup`が唯一の所有者です。PartyManagerを独立Actorにしたことで、リーダーの死亡や交代をシステムの再生成ではなく状態変更として扱えます。`AEnemyGroup`は描画や衝突を必要としませんが、ワールド上の寿命、定期的な感知、イベント、将来のStateTreeの受け皿が必要なため、情報Actorである`AInfo`を選びました。Spawnerはグループを生成して登録した後、実行時の指揮には関わりません。

パーティの知覚は敵グループを**読むだけ**で、敵側の状態を書き換えません。Formation、Target Selector、Micro Movementも、他レイヤーの結果を読み取って自分の判断だけを更新します。すべてのクラスが互いを参照するのではなく、所有者・読み取り側・実行側を分けることで、変更の影響範囲を限定しています。

→ [ADR-0006](./Docs/ADR/0006-enemy_group_combat_architecture.MD) / [ADR-0008](./Docs/ADR/0008-group_perception_engagement_separation.MD)

### 2. プレイヤーへの「譲り」を、キャラクターではなくFormationの責務にした理由

ここでいう「譲り」とは、プレイヤーが仲間の間を通ろうとしたとき、仲間が進路を空ける行動です。

各キャラクターが個別に判断すると、自分の位置しか見えないため、複数の仲間が同じ方向へ避けたり、仲間同士で譲り合って隊形を崩したりします。この判断には、隊形のスロット、他メンバーの位置、すでに譲っているメンバーの情報が必要です。

そのため、譲る対象と移動先はFormationがまとめて決め、Characterは割り当てられた移動だけを実行する構成にしました。個体の反射的な回避ではなく、共有情報を使う集団の調整として扱うことで、パーティ全体の動きを予測しやすくしています。

### 3. キャラクターの個性を中央の分岐ではなく、編集可能な部品で作る

中央管理者が「この仲間はこの敵」と決めれば結果は制御しやすい一方、性格や戦術が増えるたびに中央の条件分岐が大きくなります。そこで、ターゲット選定を小さなScore Policyの重み付き合成として表現しました。

プランナーはキャラクターBlueprint上でポリシーと重みを組み替えられ、プログラマは既存Selectorを変更せずに新しい判断軸を追加できます。実行時の状態をPolicyに持たせずComponent側へ集約したのは、Blueprintテンプレートから状態が複製される問題を防ぎ、同じ計算部品を継続評価と一回限りのAbility照準の両方で使えるようにするためです。

→ [ADR-0009](./Docs/ADR/0009-weighted_target_policy_selector.MD)

### 4. Arcを廃止し、Encircleへ変更した理由

以前の近接Arcは、同じターゲットを狙う人数`N`で弧を分割し直していました。個別ターゲットを導入すると、次のフィードバックが発生しました。

> 一人がターゲットを変更 → `N`が変化 → 残った全員を再配置 → 移動によって距離評価が変化 → 別のメンバーもターゲットを変更

ターゲット層の一つの判断が位置層全体を動かし、その移動が再びターゲット評価へ戻る、レイヤー間の振動です。また、敵の向きをArcの基準にしていたため、敵が回るだけで全員が振り付けのように回転しました。

現在のEncircleは各自の進入方向から一地点だけを求め、すでに確定した仲間と重なるときも**新しく入る側だけ**を動かします。人数と敵の向きへの依存を外し、一人の判断変更を一人の移動で終わらせました。

→ [ADR-0003 2026-08改訂](./Docs/ADR/0003-battleformation_decision_execution_split.MD)

### 5. 評価を毎フレームの「操縦者」にしない

遠距離の位置評価を毎フレーム移動先として使った結果、移動途中の現在地を選び直して止まる、プレイヤーの移動で評価軸が回り静止中の仲間まで動く、という問題が起きました。

評価は「どこが良いか」を答える相談役に戻し、コミットゲートが「今の位置を捨てるべきか」だけを判断します。一度決めた位置は次のきっかけまで保持し、実際の移動はAIControllerに任せます。**いつ決めるか、どこを選ぶか、どう移動するか**を別の責務として扱う設計です。

### 6. 戦闘位置を「固定スロット」ではなくHomeと考える

戦闘中の位置は、Formationだけでなく攻撃・回避・ギミック対応にも左右されます。スロットを「必ず立つ場所」とすると、Formationに他システムの例外条件が増え続けます。

そこでスロットを、より優先度の高い行動がないときに戻るHomeとして定義しました。攻撃や回避はHomeを消さず、一時的に上回ります。現在のMicro MovementもHomeを読むだけで、MoveToが始まれば無条件に譲ります。この考え方を、今後のMovement Intentの優先順位へ拡張します。

### 7. 敵配置は再利用Presetではなく、スポーン地点で直接組む

当初は`Line + Circle`のような完成配置をDataAsset Presetとして再利用する案を検討しました。しかし、実際に重要だったのは同じ配置の使い回しではなく、**地形と敵構成に合わせてスポーン地点ごとに異なる戦闘シーンを作ること**でした。

Preset化すると、小さな差のための複製・Override・同期規則が必要になります。そこで完成配置はSpawner内で直接組み、再利用する単位をLine / Circle / Arc / Scatterという下位Strategyに限定しました。配置を扱うプランナーが、別アセットを往復せずその場で編集・確認できることを優先した判断です。

また、Strategyは理想位置だけを作り、ワールド補正はSpawnerに集約しています。これにより、新しい並べ方を追加するときに壁・NavMesh処理を重複実装する必要がありません。

→ [ADR-0007](./Docs/ADR/0007-enemy_spawn_composite_formation.MD)

### 8. 通常AIより、コンテンツ固有の意図を優先できるようにする（今後の設計）

通常のターゲット選定とHomeは、どの戦闘でも使える既定の行動です。一方、ボスの全体攻撃から安全地帯へ逃げる、複数のギミック対象を仲間ごとに一つずつ担当する、といった行動は、通常AIより高い優先度で介入できなければなりません。

そのため、移動要求を生存・ギミック・攻撃・HomeなどのIntentとして提出し、優先度と中断可否を一つのResolverで扱う方向を考えています。また、複数の仲間への割り当ては個別StateTreeに任せず、パーティ単位のCoordinatorが決めます。全員が同じ安全地点や同じギミックへ向かうことを防ぐためです。

### 9. 仲間AIを「自動戦闘」で終わらせない（今後の検証）

『アークナイツ：エンドフィールド』は、プレイヤーが仲間のスキルを発動し、仲間がプレイヤーのターゲット付近へ移動して攻撃することで、連携を直接操作する感覚を作っています。一方、連携効率がパーティ編成を強く制約する可能性があります。『グランブルーファンタジー リリンク』は仲間の戦闘を自動化し、好きなキャラクターを比較的自由に編成できます。

本プロジェクトでは、仲間を毎回ターゲットの横へ瞬間移動させたり、プレイヤーが仲間のスキルを代行したりする方式は採用しません。しかし、完全な自動戦闘を目標にしているわけでもありません。**プレイヤーの行動に仲間が反応しつつ、特定のパーティ編成を過度に強制しない連携点**を、実際の戦闘ループを作った上で検証します。

## 🧩 検討中の課題

- **下りのトラバーサル** — 上りはジャンプ、下りはNavMesh端まで移動して自然に落下する、意図的な非対称が適切かを実際のレベルで検証
- **NavMesh境界付近のMicro Movement** — 現在の直接移動入力が、崖や狭い足場で移動可能領域を外れないための制約が必要
- **隊形ごとの追従キャッシュ** — V字とI字で必要な更新距離が異なるため、DataAsset側の設定へ移す予定
- **Movement Intentの責務** — 攻撃・回避・トラバーサル・Homeを一つの言語で扱いつつ、各システムの位置生成ロジックを吸収しすぎない境界を検証

## 🚧 ロードマップ

### 1. 仲間の攻撃 — GAS + StateTree

- GAS Abilityが攻撃を実行し、StateTreeがIdle / Approach / Attack / Recoverなどの継続状態を管理
- `SetSuppressed`、ターゲットポリシーの一回照会、Strategyへ渡す射程など、既存の接続点から段階的に導入
- StateTreeが移動を直接実行せずIntentを提出する、という責務境界を実装しながら検証

### 2. 敵グループのランタイム隊形

- `AEnemyGroup`を所有者として、前衛の盾役・後衛の遠距離役などの配置を戦闘中も維持
- スロットへ固定せず、各自が自分のHome周辺で行動できる自由度を敵側にも導入
- グループStrategyはslot / target / postureのIntentだけを出し、GAS Abilityを直接実行しない

### 3. プレイヤーと仲間の連携をゲームプレイとして検証

- 瞬間移動やスキル代行に頼らず、プレイヤーの攻撃・移動・ターゲット選択に仲間が反応する接点を試作
- 自律性、操作している感覚、自由なパーティ編成のバランスを実際の戦闘で評価

### 4. ボス戦の優先度とCoordinator

- 全体攻撃からの退避やギミック対象の分担など、通常のHome／ターゲットポリシーを上回るIntentを実装
- 複数ユニットの目的地と対象を、パーティ単位で重複なく割り当て
