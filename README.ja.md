> アクションRPG向けのスケーラブルなC++仲間AIフレームワーク。『グランブルーファンタジー リリンク』『アークナイツ：エンドフィールド』のような自然なパーティ機動の実現を目指す。

## ✨ 実装済み機能

- **3レイヤーアーキテクチャ** (Manager / Controller / Character)、役割非依存のキャラクタークラス
- **デザイナー駆動の隊形データ** (`UPrimaryDataAsset`) — 新隊形追加にコードビルド不要
- **NavMesh幅に基づくV ⇔ I自動切替** — Raycastで通路幅を測定、ヒステリシスで境界点滅防止
- **環境認識のスロット補正** — 傾斜面Z補正、NavMesh第一検証、壁スライディングはフォールバック
- **バネベースのギャップスケーリング** + **Quaternion遅延回転** — 速度で隊形が伸縮し、旋回に重みが乗る
- **スロット別距離ベースのキャッシュ無効化** — プレイヤーが離れた時のみ再算出し、通過中にスロットがプレイヤーを「追う」現象を防ぐ
- **隊形別Yield Strategy** — 抽象`UYieldStrategy`に`_Standard` / `_None`の具象。`Instanced` UPROPERTYで隊形毎に選択、`IYieldContextProvider`でComponent型から分離
- **持続停止時のHungarianスロット再割り当て** — O(N³)最適マッチング（Yielding中はスキップ）
- **Detour Crowd回避**（RVOから移行）+ コントローラーが役割を決定するシステム — 仲間が動的優先度グループでプレイヤーと互いを回避
- **戦術トラバーサル** — 経路上の段差を、射影放物線ローンチ + ベジェ進入操舵で*上り*ジャンプ（下り処理は設計中。Open Problems参照）

## 🎯 主要な設計判断

全判断の根拠を書くと長すぎるため、システムの考え方が最もよく表れるものだけを以下に挙げます。その他は`<details>`に折りたたんでいます。

### なぜキャラクターのコンポーネントではなく、独立したPartyManagerアクターにしたか

パーティシステムの生命周期は、特定キャラクターの生命周期と結合してはいけません。フォーメーションマネージャーがCharacterのコンポーネントだと、そのキャラクターが死亡・交代した瞬間にシステムが破綻します。`APartyManager`を独立アクターとして抽出することで、リーダー交代やメンバー死亡が「単純な状態変更」で済みます。同じ骨格に異なるフォーメーションコンポーネントを組み合わせれば、味方AIと敵AIでインフラを共有できます。

### なぜDetour Crowd回避を*コントローラー*が決定するのか（キャラクターではなく）

RVOからDetour Crowdへの移行で、構造的な非対称が露わになりました。Detourは「AIControllerで動くもの」を自動的にcrowdメンバーと見なしますが、プレイヤーはそのパイプラインの外にいるため、crowdエージェントとして手動登録が必要です。問題はその登録と回避役割（Leader / Normal / Yielding）を*どこで*決めるか、でした。

答えは小さなインターフェース（`ITacticalAvoidanceController`）を介したコントローラーです。憑依（Possess）を単一の起点とし、`OnPossess`ハンドラが役割を設定します。これによりプレイヤーのPawnはcrowd障害物に、AIのPawnは通常の追従者になり、**リーダー交代（= 再憑依）は追加コードなしで全く同じ経路を再利用**します。キャラクターは受動的なまま、自分の回避役割を決めません。外部システム（例：隊形のYieldロジック）は、コントローラーがプレイヤーかAIか将来の敵型かを知らずに、インターフェース越しに役割を命令します。

<details>
<summary>なぜPawnのHubコンポーネントではなく、コントローラーのインターフェースなのか</summary>

魅力的な代替案として、Pawnに「回避Hub」コンポーネントを1つ置き、プレイヤーエージェントComponentかAIのcrowd-followingComponentのどちらかへ命令をルーティングする方法があります。これは却下しました。crowd-followingComponentは*コントローラー*が所有し（PathFollowingComponentだから）、プレイヤーエージェントComponentは*Pawn*が所有します。PawnのHubは所有権の境界を越えてコントローラー内部に手を伸ばし、実行時に`if (player) / else (AI)`で分岐することになります — 分岐を消すのではなく下に押し込むだけです。インターフェースはこの分岐をコントローラーの多態性で解決し、各コントローラーは自分が所有するものだけに触れます。Hubの根拠としてよく挙がる2つのエッジケース（マルチプレイヤーの状態複製、台車など非Pawnのcrowd参加者）は、実は直交します — 複製はいずれにせよPawn側のReplicated変数の領分であり、非Pawn参加者は既にComponentベースのエージェント登録でカバーされます。どちらもインターフェースを置き換えるのではなく、その上に積み増す形になります。

</details>

### なぜYieldは隊形単位のシステムで、キャラクター単位ではないのか

より寛容な設計は各キャラクターに独自のYieldロジックを持たせ、任意の2キャラ間でYieldを成立させます。これは却下しました。キャラクター単位はN×Mの近接判定でスケールが悪く、より深刻なのは*共有コンテキストの欠如*です — 同じプレイヤーに退避する仲間が同じ場所に群がり、同一隊形内のキャラ同士が互いにYieldして隊形が崩壊します。Yieldを隊形Componentに置くことで、明確な制約を一つ受け入れます: **異なる隊形のキャラクター同士はYieldできない**。代わりに協調を行う中央の場所を得ます。これはジャンル的にも自然です — 『リリンク』『エンドフィールド』でもYieldするのはプレイヤーのパーティのみ、敵は立ち止まるか前進します。隊形を跨ぐ回避が必要ならそれはDetour Crowdの領分で、Yieldシステムではありません。*システムが何をしないか*を決めることも設計です。

### なぜYieldはStrategyパターンを使い、なぜStrategyはステートレスなのか

V隊形のYield（横+後ろに退避）とI隊形のYield（壁に張り付き、通過後に反転）は、パラメータの違いではなく構造的に別のアルゴリズムです。`UYieldStrategy`を抽象ベースとし、具象Strategyは既存コードを触らず新クラスとして追加され、`FormationDataAsset`が`Instanced` UPROPERTYとして保持するのでデザイナーが隊形毎に選べます。Strategyを**ステートレス**にしたのは、Unrealの`DataAsset`がFlyweightだからです — 複数Componentが同じAssetを共有すると`Instanced`メンバも共有され、Strategyがスロット別状態を持つとComponent間で破壊し合います。スロット別状態はすべてComponent側にあり、Strategyは問い合わせに答えるだけです。

### なぜ計画中のモード層にStateTree（Behavior Treeではなく）を使うのか

これは内部アーキテクチャの判断で — 画面には一切現れません — が、意思決定層全体のスケール性を左右するため、あえて記録します。

モード選択（平時 ↔ 戦闘、将来は危険回避）は本質的に*状態*の問題です。パーティはモードにコミットし、遷移条件が発火するまでそこに留まります。これはBehavior Treeの動き方と正反対です。BTは毎Tickルートから再走査して適切なleafを探します — *リアクティブなタスク選択*（「今この瞬間どの行動を取るか」）には正しいモデルですが、*コミット型のモード*には誤ったモデルです。Unreal公式の整理もこれと一致します: ステートマシンは実行が下降する際にState選択をコミットするのに対し、behavior treeはleafを探し続ける。コミット型モードをBTに押し込むと、Blackboardフラグで状態を擬似的に作り、全分岐を再入から守ることになります — 暗黙的で脆いステートマシンがデコレーターに散らばります。

StateTreeが適合するのは、両モデルを*結合*するからです: BTのSelectorと、ステートマシンの明示的なState・Transition。これがモード選択に必要でBTにないものを与えます:
- 各モードが自身の進入条件と遷移を所有 — 新モード（戦闘、危険回避）は既存を編集せず独立ノードとして追加（意思決定層でのOCP。Yield Strategyが追加で拡張するのと同じ構図）。
- 複合遷移（「通路が狭く*かつ*0.5秒持続*かつ*非戦闘」）が、ネストしたif/elseではなく明示的なツリーノードに。
- ヒステリシス、クールダウン、状態優先度がビルトイン（分岐毎の手書きではなく）。
- ユーティリティベースの選択（体力に応じた重みで*戦う*か*逃げる*かを選ぶ等）が標準装備 — 戦闘層に直接有用。

現在のif/elseによるV↔I切替は、ゴールではなく意図的な踏み台です: 意思決定の実際の形を露わにし、StateTree移行を*未知への飛び込み*ではなく*既知ロジックのリファクタリング*にします。**そして重要なのは、移行は「モードが複数ある」ことが前提だという点です** — 現状Idle/Followのみでは、ステートマシンは単一ノードを囲む儀式に過ぎません。正しい順序は戦闘隊形を*先に*作り（真の2つ目の状態と実際の遷移が生まれる）、その後で実際に存在する状態を管理するためStateTreeを導入することです。問題より先に道具を入れるのはStateTree自身が招く過剰設計の罠で、*いつ*それが正当化されるかを見極めるのも設計の一部です。

<details>
<summary>その他: NavMesh第一の補正、Manager/Componentの階層分離、Sphere Sweep、ヒステリシス、Facingベースのcone</summary>

**環境補正でNavMeshを第一の真実に**: 初期は*壁検知→スライド→NavMesh*の順でしたが、NavMesh外に着地したスライド結果がそのまま使われ、仲間が到達不可能な座標を目指す問題がありました。NavMesh投影を*第一の妥当性チェック*とし、壁スライディングは投影失敗時の代替探索ツールに格下げ。各ヘルパーは単一責任で、`AdjustLocationForEnvironment`は4段階のオーケストレーションとして上から下に読めます。

**Managerがモードを決め、Componentがモード内を決める**: V/I切替は平時モード内部の決定なのでComponentに置きます。戦闘モード導入時、Managerは同じ決定を取り合うのではなくアクティブなComponentを差し替える役割になります — 抽象化レベルを重ねないために。

**Line TraceではなくSphere Sweep**: Line Traceは厚み0で、カプセルが通れない隙間を通過してしまい誤判定します。カプセル半径のSphere Sweepが実際の移動フットプリントと一致します。

**切替のヒステリシス**: 単一の幅閾値は境界で点滅します。二重閾値（Narrow/Wide）で反対側へ完全に越えた時のみ発火します。

**Yieldは速度ではなくFacingで判定**: 本作はカメラと体の向きを分離しているため、静止したプレイヤーが仲間に向き直っただけでもYieldが発火すべきで、速度ベースだとその瞬間を逃します。

</details>

## 🧩 検討中の課題 (Open Problems)

開発中に観察された実際のゲームフィール課題。各項目に「なぜ起こるか」「各解決策のトレードオフ」を記録しています。

### 1. 下り段差のトラバーサル: ジャンプか自然落下か

上り段差のジャンプは動作します（放物線ローンチ + 操舵）。*下り*は別カテゴリで、初期の試みは同じ離陸点計算に誤って押し込んでいました。より深い問いはコードでなく設計です: プレイヤーは段差を「ただ歩いて降りる」のであってジャンプしません — なので仲間がジャンプで降りると不自然です。しかし「ただ歩いて降りる」はAIには難しい。`MoveTo`はNavMesh上でしか動かず、NavMeshは段差の縁で途切れるからです。

- **トレードオフ**: NavLinkで降下点をマーク（エンジン標準、堅牢だが段差毎に手動配置）vs. NavMeshの縁の先で直接移動入力にキャラを渡す「walk-off-ledge」状態（動的だが縁検知とオフメッシュ制御の短い窓が必要）。落とし所の予想: 降下はジャンプ*ではない*べき — 上り=ジャンプ、下り=歩いて落下、という意図的な非対称。

### 2. プレイヤーに押された仲間が崖から落ちる

デフォルトの物理押下に歩行可能エリアの制約がありません。『エンドフィールド』では仲間は歩行可能空間にのみ押されます。

- **方向性**: NavMeshエッジ検知 + エッジ接線方向への力ベクトル投影。

### 3. スロットキャッシュ距離閾値がV隊形に偏っている

`SlotCacheUpdateDistance`はV隊形（スロットがリーダーから遠い）向けに調整された単一のComponentレベル値です。I隊形（スロットが背後に近い）では遠いスロットだけが更新され近いスロットが更新されず、仲間が1点に集まります。

- **方向性**: 閾値を`FormationDataAsset`へ移し隊形毎に調整可能化。長期的には更新ポリシー自体がYieldと同様Strategy化し得ます。

> *解決済み:* 以前ここに挙げていた「旋回/切替後のグループ的混雑」は、RVO → Detour Crowd移行 + Hungarian再割り当てで対処しました。

## 🚧 ロードマップ

**完了済み**
- 3レイヤーアーキテクチャ、V/I隊形、NavMesh認識の環境補正、バネ補間ギャップ、Quaternion回転、V↔I自動切替
- 持続停止時のHungarian再割り当て、スロット別距離ベースのキャッシュ無効化
- Yield Strategy分離、Hungarian-Yield衝突修正
- RVO → Detour Crowd移行、コントローラーが役割を決定する回避システム（プレイヤーをエージェント化、Yield↔crowd同期）
- 上り段差の戦術トラバーサル（放物線ローンチ + ベジェ操舵）

**次**
- 下り段差のトラバーサル（Open Problem #1参照）
- `SlotCacheUpdateDistance`を`FormationDataAsset`へ移行
- Yield進行中の再評価、リーダー交代の実装（ハンドラは既に配置済み）

**それ以降**（順序付き）
- **戦闘隊形** — ターゲット相対（リーダー相対ではなく）の配置、役割制約スロット（タンク前 / ヒーラー後）。StateTreeより*先に*作る。ステートマシンを意味あるものにする真の2つ目の状態と遷移を生むため。既存システムが修正でなく追加で拡張できるかのテスト。
- **StateTree意思決定層** — 戦闘が存在したら、モード選択をComponentからStateTreeへ移行（根拠は主要な設計判断を参照）。if/elseはこれへの意図的な踏み台。
- **敵集団システム（Flockベース）** — リーダーなしの集団移動、`ATacticalCharacterBase`でインフラ再利用。
- 低優先度: `UYieldStrategy_Narrow`（通路反転）、NavLink認識ジャンプ、NavMeshエッジ回避（崖/危険 — 現テストマップでほぼ発生しないため優先度低）、スキル連携。
